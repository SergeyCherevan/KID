Я рекомендую off-screen WPF Canvas, но немного уточнил бы предыдущий план: **WPF-объекты остаются внутри runner, а IDE получает только готовые кадры**. Передавать каждую фигуру через RPC не стоит.

## 🎨 Почему именно off-screen Canvas

Сейчас API возвращает настоящие WPF-типы:

```csharp
Ellipse circle = Graphics.Circle(100, 100, 50);
circle.SetColor("Red");

var sprite = new Sprite(0, 0, circle);
sprite.Move(20, 10);
```

`Sprite` также хранит `List<UIElement>` и вычисляет столкновения по WPF-геометрии. Если IDE и пользовательский код находятся в разных процессах, передать `Ellipse` или `UIElement` через pipe невозможно.

Поэтому Canvas и все созданные элементы должны находиться рядом с пользовательской программой — внутри `KID.Runner`.

```text
Runner                              IDE
────────────────────────────────────────────────────
WPF Dispatcher
Off-screen Canvas
Rectangle/Ellipse/Sprite
Collision calculations
        │
        └── растровый кадр ───────→ WriteableBitmap
                                     внутри Canvas
```

Пользовательский код продолжает работать с теми же классами. IDE вообще не знает, какие WPF-объекты существуют в runner.

## 🧵 Модель потоков runner

Важно не выполнять пользовательский код на WPF Dispatcher:

```text
Runner
 ├─ STA-поток: Canvas, layout, render
 ├─ execution-поток: пользовательский Main
 └─ IPC-поток: Stop, input, состояние соединения
```

Это гарантирует, что:

- бесконечный пользовательский цикл не блокирует WPF Dispatcher runner;
- IPC продолжает принимать cooperative Stop;
- графические методы маршалятся через существующий `DispatcherManager`;
- IDE всё равно может принудительно завершить весь runner.

Прямое изменение WPF-элемента из пользовательского потока может вызвать thread-affinity ошибку, но это не новая несовместимость: текущий `DefaultCodeRunner` уже запускает код через `Task.Run`, а Canvas принадлежит UI-потоку IDE. Поддерживаемый путь — методы `Graphics`, `Sprite` и существующие extension methods.

## 🖼️ Как передавать кадры

Я бы не отправлял bitmap как Base64 внутри JSON. Это создаст лишние копии и примерно на треть увеличит объём.

Предлагаю два канала:

1. Управляющая named pipe:

   - Stop;
   - console;
   - keyboard/mouse;
   - canvas size;
   - diagnostics;
   - execution result.

2. Отдельный бинарный frame-канал:

   - заголовок: session, sequence, width, height, stride, DPI;
   - массив BGRA32;
   - только один незавершённый кадр;
   - устаревшие кадры можно отбрасывать.

Для Canvas 310×300 один кадр занимает около 363 КиБ. При 30 FPS это примерно 11 МиБ/с — для локального бинарного канала нормально. Для 800×600 получится около 55 МиБ/с, поэтому обязательно нужны ограничение FPS и стратегия `latest frame wins`.

Shared memory я пока не делал бы обязательной. Она добавит double buffering, синхронизацию и управление handle. Переходить к ней стоит только если benchmark покажет, что бинарная pipe не выполняет критерии производительности.

## ⏱️ Рендеринг

Runner выполняет:

```text
Measure → Arrange → UpdateLayout → RenderTargetBitmap → CopyPixels
```

WPF поддерживает создание bitmap из `Visual` через `RenderTargetBitmap`. [Документация Microsoft](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/graphics-multimedia/how-to-create-a-bitmap-from-a-visual)

Предлагаемый режим:

- максимум 30 FPS;
- рендер только во время активного выполнения;
- кадры не накапливаются;
- перед `Completed` отправляется гарантированный финальный кадр;
- после завершения runner IDE сохраняет последний bitmap на экране.

Для простых статических программ фактически будет передано несколько кадров. Для анимации — не более 30 в секунду.

## 📐 DPI и координаты

Размеры по протоколу нужно передавать в двух формах:

- logical size в WPF DIP;
- физический bitmap size с учётом `DpiScale`.

Mouse-события IDE отправляет в DIP, поэтому координаты пользовательской программы останутся такими же независимо от 100%, 125% или 150% масштабирования.

Растровый кадр необходимо создавать сразу в текущем DPI. Тогда IDE не будет растягивать низкокачественное изображение.

## 🖱️ Keyboard и Mouse

Отображаемый `Image` внутри IDE будет иметь `IsHitTestVisible="False"`, а события продолжит принимать родительский Canvas.

IDE передаёт runner:

- mouse enter/leave;
- координаты move;
- down/up/click;
- key down/up;
- text input.

Mouse move можно объединять до последнего события за кадр. Нажатия клавиш, текст и кнопки мыши отбрасывать нельзя.

Пользовательские делегаты `Keyboard.*Event` и `Mouse.*Event` существуют только в runner и исчезают вместе с процессом.

## 📏 Изменение размера Canvas

`Graphics.SetCanvasWidth/Height/Size()` сейчас обращается к визуальному дереву главного окна. В runner такого окна IDE не будет.

Этот участок следует перевести на host-команды:

1. runner немедленно меняет logical size своего Canvas;
2. отправляет `CanvasResizeRequested`;
3. IDE меняет размеры output-панели;
4. IDE возвращает фактический размер;
5. runner синхронизирует поверхность и формирует новый кадр.

`GetCanvasWidth/Height()` возвращает размер runner-поверхности, а не пытается читать окно IDE.

## 🔊 Music и файлы

Music выгоднее оставить полностью внутри runner:

- NAudio не требует графического IPC;
- процесс имеет обычные права пользователя;
- относительные пути разрешаются относительно каталога открытого `.cs` либо согласованного working directory;
- при штатном завершении вызывается `SoundPlayerOFF`;
- при hard Stop аудиоресурсы уничтожаются вместе с процессом.

## ⚠️ Ограничения подхода

- IDE получает растровое представление, а не WPF visual tree.
- Очень большой Canvas или высокая частота анимации потребуют оптимизации.
- Визуальные эффекты нужно проверить на прозрачность и DPI.
- Нужен финальный render barrier перед `Completed`.
- Нельзя делать runner-процесс долгоживущим: свежий процесс на каждый Run обеспечивает очистку статики и сборок.

Это всё же значительно менее рискованно, чем:

- переписывать публичный API на proxy-типы;
- сериализовать каждый WPF DependencyProperty;
- встраивать HWND другого WPF-процесса через `SetParent`.
