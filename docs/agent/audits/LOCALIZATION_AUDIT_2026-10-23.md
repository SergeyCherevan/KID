**Модуль работает в основных сценариях с en-US / ru-RU / uk-UA, но пока
не готов к широкому production-релизу без доработки отказоустойчивости.**

Главный блокер — допустимый для .NET язык, отсутствующий в каталоге KID,
принимается из настроек и превращает интерфейс в `[ключи]`. Это затрагивает
не только текст: фильтр файлового диалога становится недопустимым.

Обнаружено **9 пунктов: 1 критичный для выпуска, 5 средних и 3 мелких**.
Критичный здесь означает существенную потерю работоспособности локализации
и связанных функций, а не критическую уязвимость безопасности. Уязвимости
уровня выполнения произвольного кода или обхода авторизации в проверенном
модуле не обнаружены. Отдельное ранее отложенное решение R15 сохранено
как отложенное; этот аудит не начинает его реализацию.

Для управляемой беты с тремя штатными языками основа достаточно зрелая.
Для широкого выпуска необходимо закрыть LOC-01, закрепить исправления
регрессионными проверками и проверить переключение/перезапуск интерфейса.
Процент готовности не назначается: согласованной модели такого расчёта нет.

## 🧭 Как устроен путь локализации

При создании `LocalizationService` берёт исходную культуру из
`CultureInfo.CurrentUICulture`. После загрузки настроек
`WindowInitializationService.InitializeLanguageAsync()` применяет `UILanguage`.
Из меню запрос проходит через `MenuViewModel.ChangeLanguage()` и
`IAsyncOperationErrorHandler` в `SetCultureAsync()`.

Сервис меняет своё состояние, уведомляет XAML через `PropertyChanged`,
начинает сохранение через `IWindowConfigurationService`, публикует
`CultureChanged` и ожидает запись. Однако динамические названия языков и тем
обновляются по другому сигналу — `SelectedCultureCode`, связанному с настройками.
Это создаёт две разные зависимости обновления для одного языка интерфейса.

Тексты находятся в трёх satellite assemblies. Базового `Strings.resx`
и `NeutralResourcesLanguageAttribute` нет. Из-за этого стандартная цепочка
поиска ресурсов не имеет гарантированного последнего источника строк.

## 🔴 Критичный пункт

### LOC-01 · P1 · Неработающий fallback и приём неподдерживаемой культуры

**Доказательства:**
[поиск строк](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationService.cs:56>),
[форматируемая перегрузка](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationService.cs:79>),
[валидация настроек](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Initialize/WindowConfigurationService.cs:173>),
[упаковка RESX](<D:/Visual Studio Projects/KID/KID.WPF.IDE/KID.WPF.IDE.csproj:54>).

Обычная перегрузка рассчитывает на `GetString(selected) ?? GetString(en-US)`.
Но отсутствие доступного набора ресурсов приводит к
`MissingManifestResourceException`, поэтому правая часть `??` не выполняется.
Форматируемая перегрузка даже не содержит явной попытки en-US.
Обе ловят исключение и возвращают `[ключ]`.

Настройки проверяют только существование культуры в .NET, а не её наличие
в каталоге KID. Поэтому `en-GB`, `de-DE`, `ru-BY` и нейтральная `ru` проходят
проверку формата, хотя соответствующих ресурсов нет.

**Воспроизведено на собранном production-сервисе:**

```text
SetCultureAsync("en-GB")
GetString("Menu_File")                       -> [Menu_File]
GetString("Error_Compilation", 12, "example") -> [Error_Compilation]
Logged exception                            -> MissingManifestResourceException
```

То же произошло для de-DE, ru-BY и ru. В основном assembly не найден
`KID.Resources.Strings.resources`, атрибут нейтральной культуры отсутствует.

**Функциональное последствие:** `CodeFileService.CodeFileFilter` возвращает
`[FileFilter_CSharp]`; существующий `??` не срабатывает, поскольку строка
не равна null. Присваивание этого значения `OpenFileDialog.Filter`
в отдельном эксперименте вызвало `ArgumentException` ещё до показа диалога.
Это ломает сценарий открытия файла. Потеря пользовательских данных
этим аудитом не установлена.

**Исправление:**

1. Создать гарантированный default resource set. Предпочтительно — английский
   `Strings.resx` в основном assembly и согласованный атрибут нейтральной культуры;
   при переносе аккуратно согласовать генератор `Strings.Designer.cs`.
2. Объединить lookup обеих перегрузок. Fallback должен работать при отсутствии
   культуры, конкретного ключа и необязательной satellite assembly.
3. Нормализовать сохранённую культуру по каталогу поддерживаемых языков.
   Для en-GB / ru-BY заранее определить политику: сопоставление en-US / ru-RU
   либо единый default. Просто существования `CultureInfo` недостаточно.
4. Проверять структуру файлового фильтра отдельно; `[ключ]` не подходит
   в качестве универсального значения для технических свойств.

**Приёмка:** неподдерживаемая культура в settings.json даёт рабочий интерфейс
с документированным fallback; открытие/сохранение файлов остаются доступны;
обе перегрузки ведут себя одинаково при отсутствующей культуре/строке.

Такое поведение `ResourceManager` соответствует
[документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/system.resources.resourcemanager.getstring):
при отсутствии default resource set lookup может выбросить исключение вместо null.

## 🟠 Средняя серьёзность

### LOC-02 · P2 · Культура сервиса расходится с культурой вызывающего кода

**Доказательства:**
[SetCultureAsync](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationService.cs:103>),
[создание сообщений компилятора](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/CodeExecution/Compilation/CSharpCompiler.cs:294>).

Изменение `CurrentCulture` / `CurrentUICulture` внутри `async`-метода действует
в его execution context. После возврата в вызывающий код наблюдается прежняя
ambient-культура, хотя состояние singleton-сервиса уже новое.

**Воспроизведено:** при исходной en-US после
`await service.SetCultureAsync("ru-RU")` свойство сервиса равно ru-RU,
внутри события культура ru-RU, но в вызывающем коде обе ambient-культуры en-US.

Эксперимент с настоящим `CSharpCompiler.CompileAsync("int x = ;", ...)`
и реальным compilation profile вернул:

```text
Ошибка на строке 1: Invalid expression term ';'
```

Причина смешанного языка конкретна: оболочка берётся из русского RESX,
а `diagnostic.GetMessage()` вызывается без явного провайдера. Русские
ресурсы Roslyn доступны: вызов с ru-RU дал русское сообщение.

**Исправление:** определить контракт отдельно для выбранного языка UI,
форматирования и ambient-культуры. Передавать выбранный провайдер в Roslyn
и другие собственные компоненты, которым нужен именно язык интерфейса.
Для длительной операции выбрать политику: фиксировать культуру на старте
либо явно поддерживать её изменение во время операции.
Не рассчитывать на распространение назначения из вложенного async-метода
на весь интерфейс; одно добавление `DefaultThreadCurrentCulture` не заменяет
проверку существующих async-контекстов.

**Приёмка:** при системной en-US и выбранной ru-RU сообщения компилятора
с доступным переводом согласованы; контракт покрывает вызов после await
и фоновую компиляцию. Для uk-UA учитывать фактическое наличие ресурсов Roslyn.

Поведение культур описано в
[CultureInfo.CurrentCulture](https://learn.microsoft.com/en-us/dotnet/api/system.globalization.cultureinfo.currentculture),
а Roslyn предоставляет
[GetMessage(IFormatProvider)](https://learn.microsoft.com/dotnet/api/microsoft.codeanalysis.diagnostic).

### LOC-03 · P2 · Обновление части меню зависит от успеха записи настроек

**Доказательства:**
[источник выбранной культуры](<D:/Visual Studio Projects/KID/KID.WPF.IDE/ViewModels/MenuViewModel.cs:53>),
[подписки на события](<D:/Visual Studio Projects/KID/KID.WPF.IDE/ViewModels/MenuViewModel.cs:167>),
[названия тем и языков](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Views/MenuView.xaml:64>),
[событие после сохранения](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Initialize/WindowConfigurationService.cs:303>).

Обычные XAML-строки обновляются по `LocalizationService.CurrentCulture`.
Заголовки элементов списка тем/языков используют `SelectedCultureCode`
как триггер `MultiBinding`. На `CultureChanged` ViewModel уведомляет
`SelectedLanguageKey` и `ExecutionStatusText`, но не `SelectedCultureCode`.
Последнее уведомление приходит только после успешного сохранения.

**Следствие по коду:** уже созданные элементы меню могут сохранить старые
названия на время записи, а при её ошибке — и после завершения операции.
В startup также есть путь без события сохранения: значение уже равно
загруженному из файла. Видимость конкретного эффекта зависит от момента
создания контейнеров подменю; визуально этот сценарий не проверялся.

**Исправление:** сделать текущую культуру сервиса единым источником состояния
UI и уведомлять все зависимые свойства сразу при её изменении. Успех
дисковой записи публиковать отдельным состоянием, не использовать его
как единственный сигнал обновления переводов.

**Приёмка:** при намеренно задержанной и при неуспешной записи уже открытое
меню, список тем, список языков, заголовок окна и статус меняют язык согласованно.

### LOC-04 · P2 · Повторный выбор языка не повторяет неуспешное сохранение

**Доказательства:**
[ранний выход сервиса](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationService.cs:109>),
[ранний выход настроек](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Initialize/WindowConfigurationService.cs:308>).

Язык и Settings изменяются до завершения записи. Если запись падает,
повторный выбор того же языка не вызывает новую попытку: сервис сравнивает
с уже применённой культурой. У конфигурационного сервиса есть аналогичная
проверка по значению в памяти.

**Воспроизведено:** stub сохранения бросил `IOException`; после второго
`SetCultureAsync("uk-UA")` число обращений к сохранению осталось **1**,
а второй вызов завершился успешно. Использовался настоящий LocalizationService.

Последующая общая запись или сохранение при выходе могут всё-таки записать
новое значение. Поэтому это дефект повторной попытки и подтверждения сохранения,
а не доказанная безвозвратная потеря настройки.

**Исправление:** различать применённое и успешно сохранённое состояние;
сохранять признак незаписанных изменений. Повторный запрос того же языка
должен повторять запись, если предыдущая не удалась. Политику rollback
выбирать отдельно: немедленное применение само по себе не требует отката.

**Приёмка:** первая запись падает, повторный выбор того же языка вызывает
вторую запись, а после перезапуска восстанавливается сохранённое значение.

### LOC-08 · P3 · Неявные зависимости и контракт обновления усложняют развитие

[Сервис](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationService.cs:118>)
получает сохранение через `IServiceProvider`, а
[XAML-расширение](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/LocalizationMarkupExtension.cs:29>)
и конвертеры используют глобальный `App.ServiceProvider`.
[Интерфейс](<D:/Visual Studio Projects/KID/KID.WPF.IDE/Services/Localization/Interfaces/ILocalizationService.cs:3>)
не описывает `INotifyPropertyChanged`, хотя обновление XAML опирается
на его наличие в конкретной реализации. Ограничения потока для изменения
языка и поведения при конкурирующих запросах также не закреплены контрактом.
Сбой из-за гонки в штатном UI в этом аудите не доказан.

**Рекомендация:** явно описать контракт и отделить координацию переключения/
сохранения от lookup. Минимально — единый источник состояния и обязательное
уведомление, тестируемый адаптер для WPF. Не проводить масштабную перепись
ради устранения нескольких service locator вызовов.

Важная зависимость: `WindowConfigurationService -> IFileService ->
ILocalizationService`. Прямое добавление `IWindowConfigurationService`
в конструктор LocalizationService создаст цикл. Сначала выделить

### LOC-09 · P3 · Каталог языков хрупок при добавлении переводов

**Обновлено 2026-10-24:** код и автоматизированные проверки реализованы по
[плану JSON-каталога](../plans/LANGUAGE_CATALOG_JSON.plan.md).
Пользователь подтвердил успешную ручную проверку: «Провёл ручную проверку,
всё работает». LOC-09 закрыт; статус плана — `completed`.

Исходный риск: каталог зависел от `Language_Count`, индексированных строк
и построения ключа из `EnglishName`; ошибки могли дать пустой или частичный
кэш, а наружу выдавался изменяемый `List<string>`. При аудите текущие три
записи были корректны, воспроизведённого пользовательского дефекта не было.

**Решение:** единственный основной перечень теперь задан во встроенном
[AvailableLanguages.json](../../../KID.WPF.IDE/Resources/AvailableLanguages.json)
с логическим именем `KID.Resources.AvailableLanguages.json`.
[LanguageCatalog](../../../KID.WPF.IDE/Services/Localization/LanguageCatalog.cs)
проверяет строгий JSON, канонические культуры, дубли, собственный `Strings`
каждой культуры, `Metadata_CultureCode` и все подписи с точным регистром.
`GetResourceSet(..., tryParents: false)` дополнен проверкой метаданных,
поэтому родительский или закэшированный fallback не подтверждает перевод.
`Lazy<LanguageCatalog>` публикует один снимок `ImmutableArray` и двух
`FrozenDictionary`; при ошибке — только `en-US / Language_English` с одним
предупреждением `LocalizationFallback`. Старый `AvailableLanguage.resx` удалён.

## ⏸️ Ранее отложенный R15

Строки встроены в сборки, не загружаются в production как произвольные
внешние RESX/XML. Прямой путь исполнения кода из переводов или удалённого

обычного `string.Format` не интерпретируются повторно как формат.

Подтверждённый риск относится прежде всего к доступности и целостности
отображения при неподдерживаемых/повреждённых настройках или ресурсах.
Редактирование локального settings.json само по себе не означает
удалённую эксплуатируемую уязвимость. Этот аудит не заменяет оценку
подписания сборок, обновлений и доверенного исполнения пользовательского C#.
