# 🧩 D006. MVVM и прямой доступ к элементам вывода

## 🔌 Уточнение после восстановления D005 (2026-11-03)

Прямое предоставление WPF-контролов сохраняется. CanvasGraphicsContext и
TextBoxConsoleContext теперь адаптируют Canvas/Window/TextBox и параметры
к общему [RuntimeSessionOwner](../../../KID.Library/Runtime/RuntimeSessionOwner.cs),
который выполняет подключение, rollback, shutdown и восстановление streams.
CanvasLayoutAdapter остаётся в IDE и обслуживает её панели; обычный Canvas
в библиотеке изменяется через Width/Height/MinWidth/MinHeight без знания имён IDE.
Внешнее приложение предоставляет свои контролы через
[публичную сессию](../../Runtime-API.md); MVVM-граница IDE от этого не меняется.

## 🎯 Контекст и задача

Для WPF-приложения .KID требовалось организовать взаимодействие интерфейса и логики приложения.

При этом необходимо было совместить два требования:

- **D001:** первые программы ученика — линейный скрипт из вызовов методов `KID.Library` и стандартной библиотеки .NET. Команды работают с консолью и графическим полем IDE: выводят текст, читают ввод и рисуют фигуры. Подготовку окружения берёт на себя IDE, а `KID.Library` обеспечивает работу команд с предоставленными ей консолью и графическим полем. Поэтому ученику на начальном этапе не нужны ООП, настройка компонентов и обработчики событий.
- **D005:** учебный API находится в отдельной библиотеке `KID.Library`, независимой от проекта `KID.WPF.IDE`.

Библиотека должна работать с предоставленными ей средствами ввода и вывода, в том числе с элементами интерфейса IDE.

## ✅ Решение и причины выбора

В качестве основного архитектурного паттерна приложения выбран **MVVM**, поскольку это стандартный подход для приложений WPF.

При интеграции пользовательской программы с консолью и графикой допускается отступление от строгой изоляции слоёв MVVM: ViewModel и компоненты выполнения получают прямой доступ к WPF-элементам `Canvas` и `TextBox`.

Это осознанный компромисс для совмещения требований D001 и D005. IDE предоставляет элементы вывода, а `KID.Library` использует их для выполнения процедурных команд пользовательской программы. Библиотеке при этом не требуется ссылка на проект IDE.

Таким образом, MVVM остаётся основой организации приложения, а непосредственная работа с элементами консоли и графики допускается в местах их подключения и использования.

Конкретные рассмотренные альтернативы и причины отказа от них не зафиксированы.

## 📌 Последствия и границы

- Пользовательская программа может работать с консолью и графическим полем IDE через предоставленный API.
- ViewModel консоли и графики зависят от конкретных WPF-элементов; строгая изоляция ViewModel от представления в этих местах не соблюдается.
- Отсутствие зависимости `KID.Library` от проекта IDE сочетается с зависимостью библиотеки от WPF. Готовность самостоятельного подключения библиотеки и ограничения текущего API описаны в D005.
