# 🔌 D005. Контракт самостоятельного подключения KID.Library

- **Статус:** контракт этапа 1 зафиксирован; публичная сессия реализована на этапе 2, `Graphics.SetCanvas` ожидает этапа 3.
- **Дата:** 2026-11-02.
- **План:** [D005_KID.Library_STANDALONE_RESTORE.plan.md](D005_KID.Library_STANDALONE_RESTORE.plan.md).
- **Внешний потребитель:** [KID.Library.StandaloneProbe](../../../samples/KID.Library.StandaloneProbe/README.md).

Документ определяет реализацию этапов 2–6. Сигнатуры сессии/options/diagnostic
доступны в текущей сборке; выбор холста и контракт объектов ещё реализуются
на следующих этапах. Обычные учебные команды остаются статическими;
публичную сессию создаёт внешний хост, перевод IDE на неё относится к этапу 5.

## 🧩 Публичная поверхность

Все новые типы находятся в `namespace KID`, в сборке `KID.Library`.

```csharp
public sealed class KIDRuntimeOptions
{
    public System.Windows.Controls.Canvas? Canvas { get; init; }
    public System.Windows.Controls.Canvas? MouseCanvas { get; init; }
    public System.Windows.Window? KeyboardWindow { get; init; }
    public bool EnableMusic { get; init; }
    public System.Windows.Controls.TextBox? ConsoleTextBox { get; init; }
    public bool RedirectSystemConsole { get; init; }
    public Action<KIDRuntimeDiagnostic>? DiagnosticSink { get; init; }
}

public readonly record struct KIDRuntimeDiagnostic(
    long ExecutionId,
    string Component,
    string Operation,
    Exception Exception);

public sealed class KIDRuntimeSession : IAsyncDisposable
{
    public static ValueTask<KIDRuntimeSession> OpenAsync(
        KIDRuntimeOptions options,
        CancellationToken cancellationToken = default);

    public CancellationToken CancellationToken { get; }
    public void RequestStop();
    public ValueTask DisposeAsync();
}

public static partial class Graphics
{
    public static void SetCanvas(System.Windows.Controls.Canvas canvas);
    // Существующий Canvas остаётся доступным для чтения; публичного setter нет.
}
```

На этапе 1 это была спецификация без тел методов и заглушек.
`OpenAsync`/options/diagnostic реализованы на этапе 2; `SetCanvas` — задача этапа 3.

## 🔑 Открытие и состав сессии

1. В процессе допускается одна сессия. Резервирование происходит до публикации
   environment и подключения первого ресурса. Конкурентное открытие получает
   `InvalidOperationException` и не меняет существующего владельца.
2. Все nullable-параметры по умолчанию `null`, флаги — `false`. Переданный Canvas
   включает графику, MouseCanvas — мышь, KeyboardWindow — клавиатуру,
   ConsoleTextBox — консоль; музыка включается только `EnableMusic=true`.
   Отключённый компонент не создаёт ресурсы и не требует фиктивных контролов.
   Пустые options допустимы: сессия предоставляет только cooperative token.
3. `MouseCanvas` не выводится из `Canvas`, окно клавиатуры не выводится через
   `Window.GetWindow`. Необязательна даже принадлежность Canvas окну на момент
   подключения. Для обычного IDE-сценария адаптер явно передаёт все его ресурсы.
4. `RedirectSystemConsole=true` требует ConsoleTextBox, иначе
   `ArgumentException` до изменения streams. При `false` TextBoxConsole доступна
   непосредственно, но процессные `System.Console.In/Out/Error` не меняются.
5. `options == null` даёт `ArgumentNullException`. UI-контролы должны принадлежать
   одному живому Dispatcher; разные Dispatcher дают `ArgumentException` до
   публикации ресурсов. `OpenAsync` с UI-контролами вызывается на их UI-потоке;
   нарушение доступа — `InvalidOperationException`. Music-only/token-only сессии
   не создают UI Dispatcher и могут открываться с фонового потока.
6. Сессия сохраняет значения options при открытии. Внешний хост не передаёт
   execution id и не создаёт внутренние scopes. Существующий registry
   ExecutionEnvironmentManager расширяется общим admission/резервированием;
   второго registry identity не появляется. На этапе 5 IDE получает ту же
   identity и передаёт один и тот же token compiler, runner и библиотеке.
7. Уже отменённый входной token даёт `OperationCanceledException` без публикации.
   Он действует весь срок сессии, а не только во время `OpenAsync`. Сессия
   связывает его со своим STOP; `session.CancellationToken` и
   `StopManager.CurrentToken` равны до окончания cleanup. Отмена в ходе открытия
   запускает rollback перед завершением `OpenAsync` с ошибкой.

## ⏹️ STOP, нормальное завершение и ошибки

- `RequestStop()` синхронно сигнализирует отмену и закрывает приём новой работы
  этой сессии. Повторный вызов, в том числе после Dispose, безопасен и не
  затрагивает другую сессию. Pending-операции и ввод завершаются по действующим
  cooperative-контрактам C2/C3; принудительной остановки Task/потоков нет.
- Хост ожидает собственный пользовательский код. После STOP он также обязан
  вызвать и дождаться `DisposeAsync`. Сам запрос STOP не освобождает резервирование.
- `DisposeAsync` без STOP закрывает ingress до первого ожидания, сохраняет
  принятый вывод и ожидает normal drain. Он не отменяет token ради штатного
  завершения и не трактует запрошенную отмену как ошибку cleanup.
- Каждый вызов `DisposeAsync`, включая конкурентные и повторные, ожидает одну
  процедуру и получает её результат. Обязательная очистка не отменяется token
  сессии. Старый объект сессии не снимает привязки и token новой сессии.
- Частичное открытие освобождает только приобретённые ресурсы. Сохраняются
  исходная ошибка и ошибки rollback; остальные независимые шаги выполняются
  даже после первого отказа. Отмена с неуспешным rollback также сообщает ошибки
  очистки, а не маскирует их успешным STOP.
- Консоль хранит исходные In/Out/Error перед перенаправлением и независимо
  пытается восстановить каждый поток, включая частичную ошибку открытия.
  Адаптеры остаются привязаны к исходному console scope. `System.Console.Clear`
  не перехватывается библиотекой; внешний код вызывает `TextBoxConsole.Clear`.
- После неуспешного cleanup/rollback общий admission остаётся заблокированным:
  новое `OpenAsync` получает `InvalidOperationException` с причиной, IDE также
  не допускает новый Run. Снятие environment lease не снимает этот запрет.
  Публичного безусловного reset нет; успешный cleanup разрешает новое открытие.
- DiagnosticSink получает неизменяемую запись без зависимости от IDE/DI/logger.
  Callback может вызываться с разных потоков; UI-маршалинг обеспечивает хост.
  Ошибка callback уходит в Trace и не прерывает cleanup. Диагностика не подменяет
  исключения из `OpenAsync`/`DisposeAsync` и не скрывает ошибки операций.

Внутренний общий владелец должен отдельно уметь завершить библиотечные ресурсы
и окончательно освободить резервирование. Публичный Dispose объединяет эти
шаги. Адаптер IDE на этапе 5 выполняет: окончание user code → очистка библиотеки
→ освобождение running instance/ALC → финализация сессии и CTS. Ошибка любого
host cleanup также блокирует общий admission. Резервирование нельзя освобождать
между очисткой библиотеки и ALC. Эта двухфазность остаётся внутренней деталью,
а не второй реализацией lifecycle в IDE.

Хост сохраняет работающий UI Dispatcher до окончания Dispose и отписок.
Синхронное ожидание Dispose на UI-потоке недопустимо; при закрытии окна хост
временно отменяет Closing, асинхронно останавливает/ожидает свой код и сессию,
после чего окончательно закрывает окно. Видимый пример этого порядка — этап 6.

## 🎨 Выбор холста и назначение команды

- `Graphics.SetCanvas(canvas)` — синхронная смена ссылки в активной графической
  сессии. Он допускается с UI и фонового потока, без ожидания очереди UI:
  иначе нельзя безопасно выбрать B, пока принятая для A команда ждёт Dispatcher.
- `null` даёт `ArgumentNullException`; отсутствие сессии или неподключённая
  графика — `InvalidOperationException`; закрытый приём —
  `ObjectDisposedException`; другой Dispatcher — `ArgumentException`.
  Ошибка оставляет прежний Canvas. Отключения графики через `null` нет.
- Первый этап поддержки ограничен одним UI Dispatcher на сессию. Холсты
  одного Dispatcher используют общий scope. Для холста другого UI-потока нет
  скрытого маршрутизатора или неявного создания нового scope.
- Повторный выбор того же объекта допустим. A → B → A сохраняет оба изображения,
  не переносит фигуры, не очищает поля, не сбрасывает оформление и не
  переподключает Mouse/Keyboard/Music/Console. Начальное отсутствие графики
  нельзя превратить в её подключение через `SetCanvas`; используется OpenAsync.
- Вызов операции фиксирует пару «холст + владелец/scope сессии» до передачи
  делегата Dispatcher. Смена назначения после приёма не меняет эту пару.
  Согласованное владение проверяется при приёме: Canvas старой сессии никогда
  не попадает в scope новой. Закрытие admission и захват имеют определённый
  порядок; не принятая до закрытия операция отклоняется.
- Создание фигур/текста/изображений, Clear, добавление и размеры используют
  захваченный холст. Вложенный helper получает то же назначение, а не повторно
  читает Graphics.Canvas. Сохраняются проверки отмены и старого scope.
- Обязательный пример: worker поставил `Clear` для A, UI ещё занят, хост выбрал
  B, затем UI освободился — очищается A. То же правило действует для фигуры,
  возвращающей результат. Внешний probe синхронизирует реальную постановку
  через Dispatcher hooks/возврат void-команды, а не через `Sleep`.

## 🖌️ Оформление и параллельные вызовы

Цвет/шрифт остаются общими для сессии и меняются в существующей очереди UI.
Обязательного снимка оформления при вызове нет. Последовательность одного
caller «задать цвет/шрифт → нарисовать» сохраняется: нельзя прочитать старую
кисть на worker до выполнения предыдущего setter в Dispatcher. Смена холста
сама не ставит сброс стиля в очередь.

Статический выбранный Canvas общий для caller'ов. Пара «SetCanvas → команда»
в разных Task не образует независимую транзакцию; её сериализует приложение.
Дополнительный `Graphics.For(canvas)` не входит в восстановление D005.

## 🖱️ Ввод и совместимость Init

Мышь привязана к единственному `MouseCanvas` на весь срок сессии; polling и
события используют именно его, даже когда Graphics выбрала другой холст.
Неявного переключения, сброса пользовательских подписок и одновременного
ввода от нескольких полей нет. Смена источника мыши внутри сессии в этот
контракт не входит. Клавиатура аналогично привязана к явно заданному окну;
существующая KeyboardCapturePolicy сохраняется. Cleanup снимает все подписки.

Исходная совместимость исторического bootstrap `DispatcherManager.Init` /
`Graphics.Init(Canvas)` / setter StopManager.CurrentToken не восстанавливается:
возможности предоставляются новым владельцем с обязательным завершением.
Существующие публичные Mouse.Init/Keyboard.Init/Music.Init сами сессию не
создают, не используются новым примером и не получают отдельного lease.
Если ими подключён компонент текущего environment, за него отвечает тот же
общий владелец, включая проверку единого Dispatcher. Повторное подключение
уже занятого компонента остаётся ошибкой. Учебные команды не меняются.

## 🧱 Элементы, спрайты и размеры: контракт этапа 4

- Изменение существующего UIElement действует на него и его Dispatcher,
  с проверками lifecycle, независимо от выбранного графического поля.
  Поддерживаются объекты общего UI Dispatcher сессии; другой Dispatcher
  отклоняется до изменения объекта. Прямой доступ к возвращённым WPF-объектам
  остаётся ответственностью приложения и не получает обещания sandbox-изоляции.
- `AddToCanvas` добавляет отсоединённый элемент в захваченное назначение;
  наличие родителя даёт `InvalidOperationException` без неявного переноса.
  `RemoveFromCanvas` удаляет элемент из его фактического Canvas, даже когда
  выбрано другое поле; для отсоединённого элемента это no-op, для другого
  типа родителя — `InvalidOperationException`. Явный перенос: remove → выбрать
  поле → add, в той же сессии и Dispatcher.
- Принадлежность спрайта определяется фактическими родительскими Canvas его
  элементов, а не текущим Graphics.Canvas. Пустой/полностью отсоединённый
  спрайт не имеет поля и столкновений. Отсоединённые элементы не участвуют
  в столкновениях; все присоединённые элементы должны быть непосредственными
  детьми одного Canvas. Смешанные поля/неподдержанный родитель дают
  `InvalidOperationException`, другой Dispatcher — `ArgumentException`.
- GraphicElements изменяем: принадлежность проверяется при операции, а не
  только в конструкторе. Поэлементный перенос допустим, но до его завершения
  операция над смешанным спрайтом отклоняется. После полного переноса система
  координат определяется новым фактическим полем. Пустота не сбрасывает
  сохранённый execution scope и не разрешает использовать старый Sprite в новом Run.
- Спрайты разных Canvas не сталкиваются: такая пара пропускается без
  преобразования координат между окнами. Проверки валидности и stale scope
  выполняются до сравнения, включая сравниваемые спрайты. Пустой результат
  обновляет Collisions так же, как обычное отсутствие пересечения.
- В обычном WPF-хосте SetCanvasWidth/Height задают Canvas.Width/Height,
  SetCanvasMinWidth/Height — Canvas.MinWidth/MinHeight. Get возвращает
  ActualWidth/ActualHeight в DIP; результат зависит от WPF layout и ещё не
  измеренный Canvas может иметь нулевой фактический размер.
  Числовая валидация существующих команд сохраняется.
- IDE-изменения Grid/панелей живут в адаптере IDE через внутренний callback
  общего владельца с захваченным Canvas. Для собственного поля, которому
  адаптер не соответствует, действуют обычные WPF-операции над этим Canvas.
  В библиотеке нет FindName/имён WorkspaceGrid/индексов IDE-разметки.

## ✅ Проверяемые границы этапов

- **Этап 1:** Regression собирается/запускается; Session и CanvasSwitching
  содержат настоящие вызовы согласованного API и пока не компилируются.
  В `KID.sln` намеренно несобираемых проектов нет.
- **Этап 2:** Session обязан собираться и проходить. Отсутствующий SetCanvas
  ещё может блокировать только режим CanvasSwitching.
- **Этап 3:** CanvasSwitching обязан собираться и проходить. Дополнительно
  тестируются null/чужой Dispatcher/cleanup races и весь Graphics API.
- **Этапы 4–6:** проверяются правила объектов, размеров и ввода, общая
  интеграция IDE, rollback/failure admission, ALC и видимое закрытие окна.

У probe нет доступа к internals и ссылок на IDE; он дополняет KID.Tests,
который имеет обе возможности. Конкретные результаты этапа 1 записываются
в журнале [основного плана](D005_KID.Library_STANDALONE_RESTORE.plan.md).
