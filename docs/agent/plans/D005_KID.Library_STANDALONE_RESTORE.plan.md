## 🎯 1. Основание и правильная трактовка проблемы

Первоначальная причина D005 — возможность продолжать использовать знакомый учебный API после перехода из .KID IDE к собственной C#-программе в Visual Studio, Rider или другой среде. Приложение предоставляет свои WPF-элементы, библиотека выполняет команды; подключение проекта IDE не требуется.

Автор подтвердил, что до реализации C2/C3 этот сценарий работал и D005 был реализован. Исторический код подтверждает наличие необходимого публичного подключения. Следовательно, исправляется **регрессия ранее существовавшей возможности**, а не впервые реализуется первоначальный замысел.

## ✅ 2. Требования, подтверждённые обсуждением

1. Внешнее C# WPF-приложение подключает `KID.Library` без ссылки на `KID.WPF.IDE` и без специального доступа к `internal`.
2. Приложение может предоставить собственный `Canvas` и использовать знакомые статические команды библиотеки.
3. В одной программе могут существовать несколько холстов. Целевой холст можно многократно менять во время выполнения и возвращаться к ранее использованному.
4. Смена холста не требует завершать сессию, начинать новый запуск или пересоздавать консоль и музыку.
5. Команда сохраняет назначение, выбранное при её вызове: смена общего `Graphics.Canvas` не перенаправляет уже принятую операцию.
6. Для фиксации назначения используется захват ссылки в локальную переменную до передачи делегата в Dispatcher. Для нескольких холстов одного UI-потока отдельный Dispatcher scope на каждый холст не требуется.
7. При восстановлении самостоятельности сохраняются гарантии C2/C3: принадлежность ресурсов запуску, кооперативная отмена, ожидаемая очистка, защита от запоздалой очистки и запрет нового запуска при неподтверждённом завершении предыдущего.
8. В начальном сценарии IDE продолжает готовить окружение за ученика; обычные учебные команды сохраняют простую статическую форму.

## 🔭 3. Границы работы и связи с решениями

- **D001:** сохраняется переход от простого скрипта к самостоятельной организации приложения. Предоставление среды выполнения не становится обязательным занятием для начинающего пользователя IDE.
- **D002:** работа остаётся в Windows/WPF; текущая библиотека нацелена на `net10.0-windows`, использует WPF-типы в реализации и публичном API. Кроссплатформенное графическое ядро этим планом не вводится.
- **D003–D004:** Roslyn, редактор и профиль компиляции остаются обязанностью IDE. Внешнее приложение не обязано подключать их ради графики или звука.
- **D005:** восстанавливается публичный самостоятельный сценарий и реализуется требование переключения холстов.
- **D006:** сохраняется возможность передавать библиотеке реальные WPF-контролы. Полная переделка MVVM не требуется.
- **D007:** базовый запуск остаётся внутри процесса IDE с общей библиотекой и передачей WPF-операций в UI-поток.
- **D008:** сохраняется кооперативный STOP. Публичное подключение библиотеки само по себе не инструментирует код внешнего приложения; автоматическое преобразование остаётся частью Roslyn pipeline IDE.
- **D009:** `Graphics`, `Music`, `Mouse` и `Keyboard` сохраняют статические учебные точки доступа. Объект сессии, если выбран, предназначен для хоста.
- **D010:** самостоятельное подключение нынешней консоли должно иметь определённый жизненный цикл; перенаправление `System.Console` является отдельным явно выбранным действием.
- **D011:** управление окном IDE через WinAPI остаётся в IDE и не становится зависимостью внешнего хоста.

Запуск из IDE отдельного приложения **App-Window & Console** — возможное последующее применение восстановленной самостоятельности. Создание worker-процесса, межпроцессного протокола, новых режимов запуска и защитной песочницы в этот план не входит.

Несколько холстов в одном UI-потоке — обязательный сценарий приёмки. Холсты на разных UI-потоках требуют отдельного решения о маршрутизации Dispatcher; их поддержку нельзя подразумевать только по наличию переключения. Ограничение текущего этапа, если выбрано, должно быть явно проверяемым и документированным, а не скрытой ошибкой доступа к WPF.

Обязательны восстановление возможностей и сохранение учебных команд. Точная совместимость старой последовательности host-методов `Init` остаётся отдельным вопросом; заранее не обещаются ни полная совместимость, ни их обязательное удаление.

## 🧩 5. Предлагаемый способ исправления

### 5.1. Публичный владелец подключения

Рекомендуется предоставить в `KID.Library` публичный объект сессии, условно `KIDRuntimeSession : IAsyncDisposable`, с параметрами подключения, условно `KIDRuntimeOptions`.

Внешнее приложение получает поддерживаемый способ открыть окружение, передать свои ресурсы и дождаться освобождения. Внутренние `ExecutionEnvironment`, Dispatcher/input/music/console scopes не требуется делать публичными.

Общий lifecycle-компонент библиотеки используется и самостоятельным приложением, и адаптерами IDE. Не создавать две расходящиеся реализации подготовки и очистки ресурсов.

IDE сохраняет компиляцию, выполнение пользовательской точки входа, FSM интерфейса, владение running instance и выгрузку ALC. Библиотечный компонент владеет подключениями библиотеки. Сохраняется порядок: завершение пользовательского выполнения → закрытие приёма и очистка ресурсов → освобождение running instance/ALC → окончательное завершение сессии. При STOP закрытие приёма может начинаться раньше согласно действующим контрактам.

Не переносить в библиотеку зависимости от `App`, главного окна, DI-контейнера, структурного логгера или Roslyn. Для диагностики использовать простой контракт, пригодный для любого хоста; имеющийся callback диагностики может быть основой.

### 5.2. Смена назначения внутри той же сессии

Предусмотреть публичную операцию выбора холста — например, `Graphics.SetCanvas(Canvas)`; окончательное имя и выбор между методом и свойством определить на этапе контракта.

Она проверяет активность сессии и допустимость назначения, затем меняет выбранный холст. Повторный выбор того же объекта допустим и не пересоздаёт ресурсы. Смена назначения не означает новый `Init` всей сессии.

Одна активная сессия не означает один неизменяемый холст. Для нескольких `Canvas` одного UI-потока сохранить общий Dispatcher scope. Реестр отдельных scope на каждый холст только ради переключения не вводить.

Рекомендуемая семантика: переключение не очищает ни старый, ни новый холст, не переносит фигуры, не сбрасывает цвет и шрифт, не перезапускает звук и консоль. Изменение этих правил требует явного решения.

### 5.3. Захват назначения через замыкание

В каждой операции читать текущий холст до передачи делегата и далее обращаться к захваченному объекту. Пример принципа, а не готовая реализация всего контракта:

```csharp
using WpfCanvas = System.Windows.Controls.Canvas;

public static Rectangle Plot(double x, double y)
{
    var curCanvas = Canvas;

    return DispatcherManager.InvokeOnUI(() =>
    {
        if (curCanvas == null)
            throw new InvalidOperationException("Graphics Canvas is not initialized.");

        var point = new Rectangle
        {
            Width = 1,
            Height = 1,
            Fill = fillBrush,
            SnapsToDevicePixels = true
        };

        WpfCanvas.SetLeft(point, x);
        WpfCanvas.SetTop(point, y);
        curCanvas.Children.Add(point);
        return point;
    });
}
```

`SetLeft` и `SetTop` — статические методы WPF `Canvas`; их нельзя вызывать через экземпляр `curCanvas`.

Внутренний helper захвата допустим, если устраняет повторение и одновременно согласует назначение с владельцем сессии. Само переключение не должно создавать сложную систему контекстов без необходимости. При конкурентном завершении/открытии нельзя допустить пару «Canvas старой сессии + scope новой»; захват и приём операции должны проверять согласованное владение.

Вложенные операции должны сохранять назначение внешней операции, а не повторно читать изменившийся глобальный `Canvas`. Для методов, вызывающих другие публичные методы, использовать передачу захваченного значения во внутренний helper либо эквивалентное простое решение.

Захват `Canvas` не означает автоматический захват всех параметров оформления. Цвет и шрифт сейчас могут изменяться через очередь Dispatcher. Механическое чтение `fillBrush` до ранее поставленного в очередь setter способно нарушить порядок «задать цвет → нарисовать». Сохранить последовательную семантику оформления; необходимость снимка стиля определить отдельно и проверить, если он вводится.

### 5.4. Фигуры, extension-методы и спрайты

Разделить операции по смыслу:

- создание, добавление, очистка, размеры назначения — используют захваченный целевой холст;
- изменение конкретного элемента — работает с этим элементом и принадлежащим ему Dispatcher, сохраняя проверки жизненного цикла;
- удаление и перенос — имеют явно выбранную семантику владельца; смена назначения сама по себе ничего не переносит;
- спрайт и столкновения — используют определённую принадлежность/систему координат, а не текущий глобальный холст в момент выполнения.

Для спрайтов определить поведение пустого спрайта, элементов из разных холстов, явного переноса и столкновений между разными полями. Рекомендуется не считать такие поля одной системой координат без явного преобразования. Выбор «пропустить», «вернуть отсутствие столкновения» или «сообщить об ошибке» должен быть единообразным и проверенным.

Сохранить существующую защиту scope-bound спрайтов и адаптеров от использования после завершения их запуска. Не обещать изоляцию произвольного прямого доступа пользователя к возвращённым WPF-объектам.

### 5.5. Ввод, звук и консоль

Переключение графического назначения не должно неявно пересоздавать Mouse/Keyboard/Music/Console.

Для мыши определить отдельный контракт: целевой холст либо события с указанием источника; подписки и polling-state должны иметь понятную принадлежность. Сохранить простое поведение IDE с единственным полем. Режим одновременных событий от нескольких полей — открытый вопрос, а не уже согласованное расширение API.

Клавиатуру связывать с явно выбранным окном/политикой фокуса. Не предполагать, что любой `Canvas` уже присоединён к окну при создании сессии. Смена графического назначения не должна скрыто менять клавиатурное окно.

Предусмотреть выбор подключаемых компонентов: внешний хост не обязан создавать `TextBox` ради графики или `Canvas` ради музыки. В IDE оставить текущий набор ресурсов.

Для консоли явно выбирать перенаправление процессных `System.Console.In/Out/Error`; сохранять и восстанавливать каждый поток даже после ошибки очистки. Reader/writer остаются привязанными к исходному scope. Обычное внешнее приложение использует `TextBoxConsole.Clear()` явно: замена `System.Console.Clear()` выполняется только pipeline IDE.

### 5.6. Размеры холста и устройство IDE

Общие методы библиотеки должны работать с предоставленным `Canvas` без обязательных имён и индексов разметки IDE.

Изменение панелей/сплиттеров IDE выделить в адаптер IDE. Конкретную форму — небольшой callback/контракт изменения размеров либо другой локальный механизм — выбрать после проверки совместимости текущих команд. Не вводить ради этого общее кроссплатформенное графическое ядро.

Для пользовательского окна описать действие установки желаемых/минимальных размеров с учётом WPF layout. Сохранить ожидаемое управление областью вывода IDE и проверить его отдельно.

### 5.7. Обязательные инварианты завершения

- Одна активная сессия в процессе сохраняется как ограничение текущих статических фасадов; переключение холстов его не нарушает.
- Токен и идентичность сессии согласованы между библиотекой и IDE; не создаётся второй независимый registry execution identity.
- Все компоненты закрывают приём до ожидания; штатное завершение сохраняет принятый вывод, STOP обрабатывает pending-работу по существующему контракту.
- Очистка выполняется и после частичной ошибки подключения; конфликт со сторонним владельцем не даёт права его освободить.
- Повторное завершение ожидает одну процедуру; запоздалое освобождение старой сессии не снимает новые привязки.
- Ошибка одного шага не пропускает остальные независимые шаги, первичная ошибка и ошибки cleanup сохраняются.
- Session cancellation не отменяет обязательный host cleanup; токены и зависимые объекты живут до окончания использующих их операций.
- После неподтверждённой очистки общий механизм допуска запрещает новую сессию и для IDE, и для внешнего хоста. Освобождение lease само по себе не считается успешным cleanup. Не вводить безусловный публичный reset этого состояния.
- Сессия не объявляет произвольные пользовательские Task/потоки завершёнными. Хост отвечает за ожидание своего кода; библиотека — за зарегистрированные ею операции и ресурсы.
- UI Dispatcher остаётся доступным до конца отписок и UI-очистки; пример внешнего приложения показывает асинхронное завершение до окончательного закрытия окна.

## ❓ 8. Исходные вопросы перед фиксацией публичного API

Эти вопросы не отменяют согласованные требования. На Этапе 1 по каждому
зафиксирован выбор в [контракте](D005_KID.Library_STANDALONE_CONTRACT.md):
сессия `KIDRuntimeSession` с необязательными компонентами, метод `Graphics.SetCanvas`,
восстановление возможностей без старого bootstrap, фиксированные источники ввода,
принадлежность спрайтов по фактическим родителям, общий стиль без обязательного
снимка, один UI Dispatcher с ранней проверкой и общий выбор назначения между Task.
Ниже сохранены исходные формулировки вопросов как контекст этих решений.

1. **Форма подключения:** объект сессии рекомендован; окончательные имена, параметры, диагностика и обязательства хоста при закрытии определяются до реализации.
2. **Форма выбора холста:** метод `Graphics.SetCanvas`, setter свойства либо согласованный эквивалент. Нужны правила повторного выбора, `null`/отключения и времени валидации.
3. **Совместимость старых `Init`:** достаточно ли восстановления возможностей через новый контракт или требуется также исходная совместимость. Если нужен адаптер, он использует общего владельца с явным завершением, а не скрыто создаёт независимые сессии.
4. **Ввод:** мышь следует выбранному отдельно полю или получает несколько источников; как сохраняются пользовательские подписки при явной смене поля. Для клавиатуры — одно выбранное окно либо иной явно определённый контракт.
5. **Объекты и столкновения:** правила принадлежности пустых/составных спрайтов, переноса элементов и сравнения объектов разных полей.
6. **Оформление:** сохранить нынешний порядок операций без обязательного снимка стиля либо определить отдельную семантику захвата. Захват холста уже обязателен.
7. **Разные UI-потоки:** поддержать маршрутизацию по Dispatcher целевого объекта или явно ограничить первый этап общим UI-потоком с ранней проверкой. Создавать scope на каждый холст одного Dispatcher не требуется.
8. **Параллельные задачи:** общее выбранное назначение статического фасада не обеспечивает независимость пар «переключить → нарисовать» в разных задачах. Дополнительный явный API вроде `Graphics.For(canvas)` возможен, но не обязателен для восстановления последовательного сценария и не должен становиться условием простого старта.

### 10.6. Этап 5 — общий lifecycle IDE и самостоятельного хоста (2026-11-03)

Этап 5 выполнен. `CodeExecutionService` резервирует `RuntimeSessionOwner` до
создания контекста. ID выдаёт единственный `ExecutionEnvironmentManager`;
отдельный счётчик IDE удалён. `ExecutionSession` хранит FSM и completion task,
получает identity/token от общего владельца и передаёт ему Stop. Собственного
CTS и отдельного environment lease у IDE больше нет.

`CanvasGraphicsContext` и `TextBoxConsoleContext` стали адаптерами ресурсов:
первый задаёт Canvas, фиксированные источники ввода, музыку и callback размеров,
второй — TextBox и перенаправление Console. Инициализация, rollback, закрытие
приёма, ожидание workers/Dispatcher, восстановление In/Out/Error и снятие

проверки повторного Init, identity и UI target; конфликтующий адаптер не очищает
ресурсы уже подключённого владельца. `CodeExecutionContext` сохраняет снимок
дочерних адаптеров и обращается к той же идемпотентной очистке, включая partial Init.

Порядок координатора: окончание compiler/user code → закрытие приёма →
очистка контекста и библиотечных ресурсов → Dispose running instance / запрос
Unload ALC → `CompleteAsync` общего владельца с результатом host cleanup →
освобождение CTS/резервирования → Idle при полном успехе. Между библиотечной
очисткой и Dispose running instance резервирование остаётся занятым. Ошибка
любой ресурсной очистки оставляет IDE в CleaningUp и блокирует также публичную
сессию и новый экземпляр координатора; повторный Run текущего сервиса отклоняется.
Первичная ошибка выполнения сохраняется отдельно от ошибок cleanup, а один и
тот же library failure не дублируется при ожидании через несколько адаптеров.

которые уже передаются пользовательскому коду через task/SoundWait, попадали
также в результат очистки. Теперь они диагностируются как `Music/Playback`
или `Music/Auxiliary`, сохраняя fault исходной задачи. Реальные ошибки Stop,
Dispose, удаления файлов и других шагов освобождения по-прежнему дают cleanup
failure и запрещают следующий запуск. Существующий тест обработанной ошибки

Окно предоставляет два Canvas одного Dispatcher; worker в одной сессии выполняет

в Dispatcher после выхода из Closing: первая самопроверка обнаружила, что при
синхронном окончании cleanup прямой Close из Closing вызывает WPF exception.
Это исправлено, оба режима по финальному коду пройдены заново. При неподтверждённом

принудительным shutdown. Учтено также закрытие до Loaded и во время открытия.

Перед Close запускается задача, ожидающая отмены: сигнал подтверждает её старт без
случайных задержек. После Dispose проверяются окончание host task, восстановление
трёх streams, снятие статических привязок и отсутствие shutdown Dispatcher;
