- **Статус:** `proposed`; спроектировано целевое дерево, миграция не выполнена.
- **Дата:** 2026-11-02.
- **Актуализирован:** 2026-11-03, после завершения Этапов 1–6 D005 и слияния
  результата в `feature/UnifiedHarness` (HEAD `e3b9d9a`).
- **Основание:** обсуждение с автором проекта и инвентаризация текущих каталогов.
- **Объём:** место документации, решений, планов, тестов, внешних проверок,
  ручных сценариев и общих инструментов. Production-проекты не реорганизуются.

Сейчас документ находится в существующем каталоге планов. При миграции его
целевой путь — `harness/work/plans/HARNESS_STRUCTURE.plan.md`. Создавать ещё
один промежуточный каталог проектирования не требуется.

## 🎯 Назначение и основное решение

`harness/` — единый версионируемый каркас разработки KID для человека и агента.
Он объединяет контекст проекта, планирование изменений, исполняемые проверки
и общие инструменты. Документы и команды связаны с теми изменениями и
сценариями, которые они описывают и проверяют.

Четыре раздела имеют разные обязанности:

- `context/` — что представляет собой продукт, как он устроен, какие решения
  действуют и как пользоваться существующим API.
- `work/` — что предлагается изменить, какой контракт требуется получить,
  какие проблемы обнаружены и по каким критериям работа завершается.
- `checks/` — как проверить фактическое поведение и где находятся
  воспроизводимые сценарии и существенные результаты проверки.
- `tools/` — общие команды подготовки и запуска проверок.

Авторство документа не определяет его расположение. Раздел `agent/`
исчезает: архитектурные решения, написанные человеком или агентом,
имеют одинаковое назначение и один источник истины.

## 🚪 Точки входа

- **Корневой README.md:** обзор продукта из нынешнего `docs/README.md`,
  быстрый запуск IDE, ссылка на учебные материалы и на `harness/README.md`.
- **Корневой AGENTS.md:** краткая маршрутизация по репозиторию и правила
  обращения с harness. Подробности архитектуры и команд остаются в своих
  документах; содержимое AGENTS.md определяется при миграции отдельно.
- **harness/README.md:** карта четырёх разделов, базовый порядок разработки,
  маршруты к действующим решениям, текущим планам и проверкам.
- **Invoke-Harness.ps1:** общий запуск повторяемых операций. Сейчас файла нет;
  предлагаемый интерфейс команд, сценариев и exit codes описан в разделе
  «Интерфейс Invoke-Harness.ps1». Реализация выполняется на Этапе 5 миграции.

Корневые входы дают короткие ссылки; harness содержит полную информацию.
Команды `dotnet` через корневой KID.sln остаются поддерживаемыми. Будущий
runner использует те же сборки и проверки, не создавая второй реализации.

## ⚙️ Интерфейс Invoke-Harness.ps1

**Статус:** `proposed`; спроектирован первый интерфейс, скрипт ещё не создан.
Пути и примеры ниже относятся к структуре после миграции. Runner рассчитан
на PowerShell 7+; сборки и проверки WPF выполняются на Windows. SDK выбирается
по корневому `global.json` (`10.0.100`, `rollForward: latestFeature`, без preview),
а не фиксируется вторым независимым правилом внутри скрипта.

### Команды и состав операций

Синтаксис: `./harness/tools/Invoke-Harness.ps1 -Command <команда> [параметры]`.
`-Command` необязателен: запуск без аргументов показывает `help`.
Имена команд и значения перечислений сравниваются без учёта регистра.

- **`help`** — синтаксис, команды, значения по умолчанию, профили и exit codes.
  Не требует dotnet, не создаёт артефактов и не запускает проверки.
- **`doctor`** — проверить PowerShell/Windows, доступность dotnet, выбранный
  по global.json SDK и наличие solution, трёх проверочных проектов и ручных
  README в ожидаемых местах. Вывести найденные версии и пути. Не делать
  restore/build, не менять настройки и не объявлять тесты пройденными.
  Наличие рабочего desktop-сеанса проверяется непосредственно перед demo.
- **`build`** — restore и Release-сборка KID.sln (либо Debug по параметру).
  Внешние проекты в эту команду не входят; они готовятся командами probe/demo.
- **`test`** — restore, сборка solution и запуск всех тестов через KID.sln.
  После успешной сборки использовать `dotnet test ... --no-build --no-restore`
  в той же конфигурации. Существующий выбор Microsoft.Testing.Platform
  из global.json сохраняется; runner не внедряет другой test runner.
- **`probe`** — restore внешнего probe, затем сборка и запуск каждого выбранного
  режима в отдельном процессе. `-Mode All` выбирает `Regression`, `Session`,
  `SessionFailure`, `CanvasSwitching`, `CanvasObjects` именно в таком порядке.
  Режим передаётся как MSBuild property `StandaloneContractStage`.
- **`demo`** — restore и отдельная сборка WPF demo, затем самопроверки окна.
  `-ConsoleMode Without` запускает `--verify`, `With` —
  `--verify --with-console`, `Both` — оба последовательно в разных процессах.
  Успех учитывается после завершения процесса с code 0. Команда явно
  открывает окна; физический ввод и слышимость звука остаются ручной приёмкой.
- **`check`** — согласованный автоматический прогон с предварительной проверкой
  окружения. Профиль `Headless`: build solution → все тесты → все пять probe.
  Профиль `Full`: тот же набор → обе самопроверки demo. Restore и сборка
  solution выполняются один раз за прогон, demo собирается один раз перед
  двумя запусками. Общие внутренние операции используются и отдельными командами.
- **`manual`** — вывести путь и содержимое README выбранного ручного сценария,
  включая команды подготовки, запуска и восстановления. При `-Scenario All`
  вывести перечень пяти сценариев и пути README. Это информационная команда;
  она не запускает IDE, сервер, звук или recovery-скрипты и не ставит PASS.

Полный автоматический набор миграции — `check -Profile Full`.
`Headless` пригоден для регулярного прогона без окон; итог явно указывает
профиль и выбранные проверки. Проверка Markdown-ссылок, анализ старых путей
и ручная приёмка остаются отдельными пунктами Этапа 6, а не подразумеваются
результатом `check`. HTTP fixture музыки запускается командами из её README;
`MusicDownloadSmoke.cs` открывается в KID и не запускается через dotnet.

### Параметры и допустимые сочетания

- **`-Command`**: `help | doctor | build | test | probe | demo | check | manual`.
  По умолчанию `help`; для справки также поддерживается `-Help` без других
  рабочих параметров.
- **`-Configuration`**: `Release | Debug`, по умолчанию `Release`.
  Допустим для build/test/probe/demo/check; используется одинаково для всех
  дочерних сборок и запусков текущего вызова.
- **`-NoRestore`**: переключатель для build/test/probe/demo/check.
  По умолчанию restore выполняется для всех участвующих проектов, включая
  внешние проекты, которых нет в solution. С этим параметром каждая dotnet-команда
  получает `--no-restore`; отсутствующие assets/cache дают ошибку, автоматического
  отката к сетевому restore нет. Подразумеваемого `--no-build` параметр не даёт.
- **`-Mode`**: `All | Regression | Session | SessionFailure | CanvasSwitching |
  CanvasObjects`, по умолчанию `All`; только для probe.
- **`-ConsoleMode`**: `Both | Without | With`, по умолчанию `Both`;
  только для demo. Обычное интерактивное окно без `--verify` запускается
  прямой командой из standalone README.
- **`-Profile`**: `Headless | Full`, по умолчанию `Headless`; только для check.
  Full всегда включает пять probe и обе проверки demo; сокращать этот набор
  параметрами Mode/ConsoleMode нельзя.
- **`-Scenario`**: `All | standalone-library | music-download |
  first-launch-language | persistence-recovery | editor-session-recovery`,
  по умолчанию `All`; только для manual.
- **`-TimeoutSeconds`**: целое от 1 до 86400, по умолчанию `600`;
  для build/test/probe/demo/check. Это предел каждого отдельного дочернего
  процесса, включая restore/build, а не всего прогона.

Неизвестный параметр, неизвестное значение или параметр чужой команды —
ошибка использования до запуска процессов. Например, `test -Mode Session`
и `check -Profile Full -Mode Regression` отклоняются. Проверка учитывает
явно переданные параметры; значения по умолчанию чужих команд ей не мешают.
Произвольная строка дополнительных shell/dotnet-аргументов в первый интерфейс
не входит; целевые запуски с test filters доступны прямыми dotnet-командами.

### Выполнение, restore и изоляция режимов

Корень определяется от `$PSScriptRoot` (два уровня выше tools), проверяется
по KID.sln/global.json и используется как рабочий каталог дочерних команд.
Исходный текущий каталог вызывающего процесса сохраняется. Аргументы дочерних
процессов передаются массивом, без строковой сборки shell-команды; пути с
пробелами должны поддерживаться.

Операции идут последовательно. При первом отказе runner останавливает прогон,
показывает отказавшую операцию, остальные отмечает `not-run`; общего PASS нет.
`SessionFailure` намеренно проверяет запрет новой сессии внутри своего процесса:
его code 0 означает успех проверки и позволяет перейти к следующему процессу.

Для probe перед каждым режимом используется эквивалент
`dotnet run --project <probe> -c <configuration> --no-restore
-p:StandaloneContractStage=<mode>`. Сборка каждого режима обязательна:
состав Compile определяется свойством MSBuild, имя итоговой сборки общее.
Повторное использование бинарника через `--no-build` или параллельная сборка
режимов в общий bin/obj недопустимы. При реализации проверить последовательность
All по фактическим описаниям сценариев в выводе. Для demo `--no-build` допустим
после успешной сборки именно этого проекта в выбранной конфигурации.

Нельзя запускать два изменяющих сборочные артефакты прогона одновременно
в одном checkout. Runner использует общий lock с метаданными процесса
в `artifacts/harness/`; занятый lock даёт ошибку окружения. Lock освобождается
в finally и при завершении процесса; оставшийся файл сам по себе не означает
занятость. Help/doctor/manual не требуют lock. Это ограничение runner;
прямые dotnet-запуски пользователь согласует самостоятельно.

При превышении timeout runner фиксирует timeout и останавливает только своё
дерево дочерних процессов. При Ctrl+C отменяет текущую операцию, прекращает
дальнейшие запуски и освобождает lock. Принудительное завершение после timeout
не считается успешной очисткой сессии или закрытием WPF-окна.

### Результаты и коды завершения

Рабочий запуск создаёт уникальный каталог
`artifacts/harness/<UTC timestamp>-<run id>/`. Он содержит лог каждой операции,
TRX тестов (через параметры текущего test runner) и `summary.json`.
Обычные bin/obj остаются рядом с проектами; перенастройка всей схемы MSBuild
output paths в первый runner не входит.

Сводка содержит command/profile/выбор режимов, конфигурацию, NoRestore,
revision и признак dirty (если доступен Git), версии среды, время начала/конца,
список операций с аргументами, рабочим каталогом, длительностью, исходным exit
code дочернего процесса, статусом и путём лога. Если Git недоступен, revision
помечается `unknown`; сборки от Git не зависят. Изменение файлов во время
прогона не превращает исходную revision в доказательство проверки нового кода.

Статусы операции: `passed`, `failed`, `timed-out`, `cancelled`, `not-run`.
Информационные команды не создают каталоги и выводят `INFO`, рабочие —
`PASS/FAIL` с точным составом выполненных проверок и путём сводки.
Summary записывается также при отказе и отмене, насколько позволяет завершение
процесса. Ошибка записи обязательных артефактов не маскируется общим PASS.

- **`0`** — выбранная операция/набор прошёл либо информационный вывод выполнен.
  `build` не означает прохождение тестов; `manual` не означает ручную приёмку.
- **`1`** — дочерняя команда завершилась ненулевым кодом или проверка не прошла.
  Исходный код сохраняется в логе и summary, а не подменяет классификацию runner.
- **`2`** — неверная команда, значение или сочетание параметров.
- **`3`** — недоступно требуемое окружение: SDK/файлы/desktop, каталог артефактов
  или lock. Недоступный desktop в Full не преобразуется в пропуск с code 0.
- **`4`** — внутренняя ошибка runner или ошибка сохранения обязательного результата.
- **`124`** — дочерний процесс превысил timeout.
- **`130`** — прогон отменён пользователем.

Граница кодов относится к ошибкам, обработанным запущенным runner;
ошибка запуска самого PowerShell или разбора повреждённого скрипта остаётся
ошибкой среды. Для Full desktop проверяется до начала сборок; при успешной
предпроверке реальный исход создания/закрытия окна всё равно определяет demo.

### Проверка реализации интерфейса

На Этапе 5 проверить справку без dotnet, ошибки параметров до запуска процессов,
путь с пробелами и чужой текущий каталог, выбор конфигурации, NoRestore без

второго runner при занятом lock. Отдельно проверить, что Headless не открывает
окон, Full не сокращает состав, а все пять probe действительно пересобираются
и выполняют свои сценарии. Проверка summary должна сопоставлять его операции
с логами; проверять текст реализации тестами, повторяющими его устройство,

Текущий API описывается в `context/api/`; контракт изменения находится

может сохраняться как основание приёмки и история требований; актуальный
API-справочник описывает фактическое поведение. Для завершённого D005 это
`Runtime-API.md` и связанные справочники, а не первоначальный контракт Этапа 1.
Не создаётся второй справочник с независимым описанием того же API.

### Исполняемые проверки

- Весь `KID.Tests/` → `harness/checks/automated/KID.Tests/`. Имя проекта,
  AssemblyName, namespaces, friend-разрешения и состав проверок сохраняются.
  Каталог называется automated, поскольку проект содержит и компонентные,
  и интеграционные/lifecycle-тесты.
- `samples/KID.Library.StandaloneProbe/`
  → `harness/checks/probes/KID.Library.StandaloneProbe/`.
  Он сохраняет уникальную сборку, единственную ProjectReference на библиотеку
  и отсутствие friend-доступа. Слияния с KID.Tests нет.
- Все пять режимов probe реализованы: `Regression`, `Session`, `SessionFailure`,
  `CanvasSwitching`, `CanvasObjects`. После миграции каждый запускается отдельно
  через `StandaloneContractStage`; обычная сборка проверяет только выбранный
  режим (по умолчанию `Regression`) и не заменяет полный набор.
  `Regression` проверяет отказ старых команд подключить окружение без сессии,
  а восстановленную самостоятельность подтверждают остальные режимы.
- `samples/KID.Library.StandaloneDemo/`
  → `harness/checks/probes/KID.Library.StandaloneDemo/`.
  Это внешний WPF-хост, одновременно показывающий использование API и
  проверяющий lifecycle реального окна. Поэтому он хранится рядом с probe;
  инструкция ручной приёмки ссылается на него без копирования исходников.
  Сохраняются уникальная сборка `KID.Standalone.Demo.D005`, единственная
  ProjectReference на библиотеку и отсутствие friend-доступа.
- Оба внешних проекта остаются вне `KID.sln`; runner запускает их явно.
  Probe работает без видимого окна; demo в режимах `--verify` и
  `--verify --with-console` открывает настоящее WPF-окно и требует отдельного
  запуска. Условия headless-тестов KID.Tests этим не меняются.
- `docs/testing/STANDALONE_LIBRARY.smoke.md`
  → `manual/standalone-library/README.md`: собственное окно без/с консолью,
  ввод, звук, STOP, закрытие и интеграция IDE. Самопроверки demo дополняют
  этот сценарий, но не подтверждают его визуальный/звуковой результат.
- `docs/testing/MUSIC_DOWNLOAD.smoke.md` и два соответствующих `.cs`
  из `scripts/manual-checks/` → один каталог `manual/music-download/`;
  инструкция становится README.md.
- `docs/testing/FIRST_LAUNCH_LANGUAGE.smoke.md`
  → `manual/first-launch-language/README.md`.
- Каждый recovery `.ps1` → свой сценарий `manual/*-recovery/`.
  Для них при миграции нужны короткие README с параметрами, подготовкой,
  ожидаемым результатом и восстановлением исходного состояния.

Fixture или подготовительный скрипт, принадлежащий одному сценарию,
находится рядом с ним. В `tools/` выносится код, реально используемый
несколькими сценариями или общим runner. Существующие Infrastructure и
TestDoubles внутри KID.Tests остаются внутренними средствами этого проекта.

## 🔗 Как harness связывает работу и проверку

План изменения ссылается на исходные решения, контракт, конкретные проверки
и критерии завершения. README сценария указывает, какое поведение проверяет,
как его воспроизвести и что считается успехом. Результат содержит ссылку
на сценарий, проверенную revision, дату, окружение и фактический исход.

Для D005 это означает:

```text
context/decisions/D005_…md
  → work/plans/D005_…plan.md + work/contracts/D005_…md
  → checks/automated/KID.Tests/… + checks/probes/KID.Library.StandaloneProbe/
    + checks/probes/KID.Library.StandaloneDemo/ + checks/manual/standalone-library/
  → фактический результат проверки конкретной revision
```

`checks/evidence/` хранит только существенные версионируемые протоколы:
например, ручную визуальную/звуковую приёмку или воспроизведение отказа,
которое не выражено обычным тестом. Каталог появляется с первым таким файлом.
Для краткого итога автоматического прогона достаточно записи в журнале плана;
отдельный дублирующий протокол для каждого запуска не создаётся.

TRX/XML, бинарники, screenshots каждого автоматического прогона, временные
settings, загрузки и прочие генерируемые данные не коммитятся. Новые общие
команды направляют результаты в `artifacts/harness/`. Обычные dotnet-команды
могут сохранять gitignored bin/obj рядом с проектами. Продуктовые runtime-логи
и пользовательские настройки не переносятся из их штатных расположений.

## 📏 Правила поддержания структуры

1. Каждый материал имеет одно каноническое место, выбранное по его обязанности.
   Ссылки и короткие указатели допустимы; копии содержимого для разных читателей
   не создаются.
2. Новый сценарий проверки создаётся целиком в checks: инструкция, код,
   локальные fixtures и описание cleanup. Общие инструменты остаются в tools.
3. Учебные примеры для пользователя относятся к course; внешнее приложение,
   проверяющее публичный контракт, относится к checks/probes.
4. Исходный код и воспроизводимые проверки определяют фактическое поведение.
   Context описывает это поведение; plans/contracts явно отделяют предполагаемые
   изменения от реализованных и сохраняют статус и основания приёмки.
5. Решения сохраняют причины выбора и ограничения. План имеет статус;
   завершение подтверждается его критериями и реальными проверками.
   Неактуальные планы без самостоятельной ценности сохраняются в Git-истории,
   без нового общего каталога archive «на всякий случай».
6. Новые каталоги используют английские имена lower-kebab-case. Существующие
   имена .NET-проектов, C#-типов и документов при переносе сохраняются,
   кроме превращения инструкции отдельного сценария в README.md.
7. Новая верхнеуровневая папка требует объяснения обязанности, которую
   не покрывают существующие разделы. Один новый скрипт или формат файла
   сам по себе не служит основанием нового раздела.

## 🛠️ Границы будущей миграции

Эта работа сейчас создаёт только проект структуры. Отдельная миграция должна
обновить KID.sln, ProjectReference, действующие команды, Markdown-ссылки,
путевые ссылки в документации и подсказки восстановления в `.ps1`.
После переноса все три проверочных проекта (KID.Tests, StandaloneProbe,
StandaloneDemo) ссылаются на production-проекты через четыре уровня `..`;
их assembly identity не меняется.

При переносе контракта D005 необходимо уточнить его исторический статус:
в текущей шапке ещё указано ожидание Этапа 3, хотя `Graphics.SetCanvas` уже
реализован и весь план D005 завершён. Исходные требования и свидетельства
Этапа 1 сохраняются; актуальное описание API остаётся в `context/api/`.

Пути внутри исторических `git show <commit>:<path>` и журналы реально
выполненных команд сохраняются как свидетельства своего среза. Для новых
запусков рядом указывается актуальный маршрут. Безусловная текстовая замена
всех старых путей испортила бы историческую доказательную базу.

Миграция завершается проверкой ссылок и сборочного графа, Release build/test
основного solution, запуском всех пяти режимов probe, отдельной Release-сборкой
demo и обеими его самопроверками окна, а также проверкой доступности команд
ручных сценариев. После переноса команды используют новые пути из целевого
дерева. Переезд не считается подтверждением визуального/звукового результата.
Реализация D005 завершена до миграции; изменение её API и lifecycle в перенос
не входит.
