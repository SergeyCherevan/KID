# 🧭 Единая структура harness разработки KID

- **Статус:** `proposed`; спроектировано целевое дерево, миграция не выполнена.
- **Дата:** 2026-11-02.
- **Основание:** обсуждение с автором проекта и инвентаризация текущих каталогов.
- **Объём:** место документации, решений, планов, тестов, внешних проверок,
  ручных сценариев и общих инструментов. Production-проекты не реорганизуются.

Сейчас документ находится в существующем каталоге планов. При миграции его
целевой путь — `harness/work/plans/HARNESS_STRUCTURE.plan.md`. Создавать ещё
один промежуточный каталог проектирования не требуется.

## 🎯 Назначение и основное решение

`harness/` — единый версионируемый каркас разработки KID для человека и агента.
Он объединяет контекст проекта, планирование изменений, исполняемые проверки
и общие инструменты. Документы и команды связаны с теми изменениями и
сценариями, которые они описывают и проверяют.

Четыре раздела имеют разные обязанности:

- `context/` — что представляет собой продукт, как он устроен, какие решения
  действуют и как пользоваться существующим API.
- `work/` — что предлагается изменить, какой контракт требуется получить,
  какие проблемы обнаружены и по каким критериям работа завершается.
- `checks/` — как проверить фактическое поведение и где находятся
  воспроизводимые сценарии и существенные результаты проверки.
- `tools/` — общие команды подготовки и запуска проверок.

Авторство документа не определяет его расположение. Раздел `agent/`
исчезает: архитектурные решения, написанные человеком или агентом,
имеют одинаковое назначение и один источник истины.

каноническое место внутри harness. Постоянных копий и symlink-зеркал нет.

`course/` остаётся рядом с production-проектами как учебный материал продукта.
`.git/`, `.vs/` и прочие локальные служебные каталоги не становятся содержимым
harness. `.github/`, `.vscode/`, solution и конфигурация SDK сохраняют свои
стандартные точки входа. Исполнение конкретной CI-конфигурации этим деревом
не подразумевается: при инвентаризации `.github/` не содержал файлов.

## 🚪 Точки входа

- **Корневой README.md:** обзор продукта из нынешнего `docs/README.md`,
  быстрый запуск IDE, ссылка на учебные материалы и на `harness/README.md`.
- **Корневой AGENTS.md:** краткая маршрутизация по репозиторию и правила
  обращения с harness. Подробности архитектуры и команд остаются в своих
  документах; содержимое AGENTS.md определяется при миграции отдельно.
- **harness/README.md:** карта четырёх разделов, базовый порядок разработки,
  маршруты к действующим решениям, текущим планам и проверкам.
- **Invoke-Harness.ps1:** общий запуск повторяемых операций. Сейчас файла нет;
  интерфейс команд, сценариев и exit codes проектируется отдельным шагом.

Корневые входы дают короткие ссылки; harness содержит полную информацию.
Команды `dotnet` через корневой KID.sln остаются поддерживаемыми. Будущий
runner использует те же сборки и проверки, не создавая второй реализации.

## 📍 Размещение существующих материалов

### Контекст и рабочие документы

- `docs/README.md` → корневой `README.md` с актуальной картой репозитория.
- `docs/FEATURES.md`, `docs/DEVELOPMENT.md` → `harness/context/`.
- `docs/ARCHITECTURE.md`, `docs/SUBSYSTEMS.md`, `docs/CodeExecution.md`
  → `harness/context/architecture/`.
- Шесть `docs/*-API.md` → `harness/context/api/`.
- `docs/references/*` → `harness/context/references/`.
- `docs/agent/decisions/*` → `harness/context/decisions/`.
- Файлы планов из `docs/agent/plans/` → `harness/work/plans/`.
  Исключение по назначению: D005_STANDALONE_CONTRACT → `work/contracts/`.
- `docs/agent/audits/*` → `harness/work/audits/`.
- Правила навигации, статусов и актуальности из `docs/agent/README.md`
  включаются в `harness/README.md`; происхождение «создано агентом» больше
  не определяет каталог.

Текущий API описывается в `context/api/`; контракт ещё не реализованного
изменения находится в `work/contracts/` и прямо обозначает свой статус.
После реализации API-справочник обновляется по фактическому поведению.
Не создаётся второй справочник с независимым описанием того же API.

### Исполняемые проверки

- Весь `KID.Tests/` → `harness/checks/automated/KID.Tests/`. Имя проекта,
  AssemblyName, namespaces, friend-разрешения и состав проверок сохраняются.
  Каталог называется automated, поскольку проект содержит и компонентные,
  и интеграционные/lifecycle-тесты.
- `samples/KID.Library.StandaloneProbe/`
  → `harness/checks/probes/KID.Library.StandaloneProbe/`.
  Он сохраняет уникальную сборку, единственную ProjectReference на библиотеку
  и отсутствие friend-доступа. Слияния с KID.Tests нет.
- Probe остаётся вне обычной сборки solution, пока его будущие режимы
  намеренно не компилируются. Включение в общий gate делается явно для
  согласованного режима; ожидаемая ошибка никогда не маскируется PASS.
- `docs/testing/MUSIC_DOWNLOAD.smoke.md` и два соответствующих `.cs`
  из `scripts/manual-checks/` → один каталог `manual/music-download/`;
  инструкция становится README.md.
- `docs/testing/FIRST_LAUNCH_LANGUAGE.smoke.md`
  → `manual/first-launch-language/README.md`.
- Каждый recovery `.ps1` → свой сценарий `manual/*-recovery/`.
  Для них при миграции нужны короткие README с параметрами, подготовкой,
  ожидаемым результатом и восстановлением исходного состояния.

Fixture или подготовительный скрипт, принадлежащий одному сценарию,
находится рядом с ним. В `tools/` выносится код, реально используемый
несколькими сценариями или общим runner. Существующие Infrastructure и
TestDoubles внутри KID.Tests остаются внутренними средствами этого проекта.

## 🔗 Как harness связывает работу и проверку

План изменения ссылается на исходные решения, контракт, конкретные проверки
и критерии завершения. README сценария указывает, какое поведение проверяет,
как его воспроизвести и что считается успехом. Результат содержит ссылку
на сценарий, проверенную revision, дату, окружение и фактический исход.

Для D005 это означает:

```text
context/decisions/D005_…md
  → work/plans/D005_…plan.md + work/contracts/D005_…md
  → checks/automated/KID.Tests/… + checks/probes/KID.Library.StandaloneProbe/
  → фактический результат проверки конкретной revision
```

`checks/evidence/` хранит только существенные версионируемые протоколы:
например, ручную визуальную/звуковую приёмку или воспроизведение отказа,
которое не выражено обычным тестом. Каталог появляется с первым таким файлом.
Для краткого итога автоматического прогона достаточно записи в журнале плана;
отдельный дублирующий протокол для каждого запуска не создаётся.

TRX/XML, бинарники, screenshots каждого автоматического прогона, временные
settings, загрузки и прочие генерируемые данные не коммитятся. Новые общие
команды направляют результаты в `artifacts/harness/`. Обычные dotnet-команды
могут сохранять gitignored bin/obj рядом с проектами. Продуктовые runtime-логи
и пользовательские настройки не переносятся из их штатных расположений.

## 📏 Правила поддержания структуры

1. Каждый материал имеет одно каноническое место, выбранное по его обязанности.
   Ссылки и короткие указатели допустимы; копии содержимого для разных читателей
   не создаются.
2. Новый сценарий проверки создаётся целиком в checks: инструкция, код,
   локальные fixtures и описание cleanup. Общие инструменты остаются в tools.
3. Учебные примеры для пользователя относятся к course; внешнее приложение,
   проверяющее публичный контракт, относится к checks/probes.
4. Исходный код и воспроизводимые проверки определяют фактическое поведение.
   Context описывает это поведение; plans/contracts обозначают предполагаемые
   изменения и не объявляют их реализованными.
5. Решения сохраняют причины выбора и ограничения. План имеет статус;
   завершение подтверждается его критериями и реальными проверками.
   Неактуальные планы без самостоятельной ценности сохраняются в Git-истории,
   без нового общего каталога archive «на всякий случай».
6. Новые каталоги используют английские имена lower-kebab-case. Существующие
   имена .NET-проектов, C#-типов и документов при переносе сохраняются,
   кроме превращения инструкции отдельного сценария в README.md.
7. Новая верхнеуровневая папка требует объяснения обязанности, которую
   не покрывают существующие разделы. Один новый скрипт или формат файла
   сам по себе не служит основанием нового раздела.

## 🛠️ Границы будущей миграции

Эта работа сейчас создаёт только проект структуры. Отдельная миграция должна
обновить KID.sln, ProjectReference, действующие команды, Markdown-ссылки,
путевые ссылки в документации и подсказки восстановления в `.ps1`.
После переноса оба проверочных проекта ссылаются на production-проекты
через четыре уровня `..`; их assembly identity не меняется.

Пути внутри исторических `git show <commit>:<path>` и журналы реально
выполненных команд сохраняются как свидетельства своего среза. Для новых
запусков рядом указывается актуальный маршрут. Безусловная текстовая замена
всех старых путей испортила бы историческую доказательную базу.

Миграция завершается проверкой ссылок и сборочного графа, Release build/test
основного solution, проверкой внешнего probe в согласованном режиме и
доступности команд ручных сценариев. Переезд не считается подтверждением
их визуального/звукового результата. Перенос и содержание API D005 — разные
изменения; Этап 2 D005 в этом проектировании не реализуется.
