# 🌐 LOC-09: переход на встроенный JSON-каталог языков

**Статус:** `implemented` — код и автоматизированные проверки выполнены
2026-10-24; ожидается ручная приёмка меню (§ 9.3), поэтому статус не `completed`.

**Основание:** [LOC-09 в аудите локализации](../audits/LOCALIZATION_AUDIT_2026-10-23.md#loc-09--p3--каталог-языков-хрупок-при-добавлении-переводов).

**Цель:** заменить индексированный каталог `AvailableLanguage.resx` на
`AvailableLanguages.json`, встроенный в сборку как `EmbeddedResource`,
с проверкой данных и неизменяемым представлением в памяти.

## ✅ 1. Согласованное решение и границы

- Источник основного перечня языков — JSON в репозитории.
- JSON встраивается в сборку приложения. Изменение каталога требует пересборки.
- Запись содержит `cultureCode` и `displayNameKey`.
- Переведённые подписи остаются в `Strings.*.resx`.
- Счётчик, числовые индексы и вычисление ключа из `EnglishName` удаляются.
- Перечень трёх языков не переносится в массив записей в C#.

Ниже зафиксированы детали реализации: строгая проверка всего каталога,
однократная загрузка, неизменяемый снимок и аварийная запись английского
языка. Эти детали конкретизируют согласованное хранение в JSON.

В рамках LOC-09 сохраняются публичный интерфейс `ILocalizationService`,
порядок языков, ключи пунктов меню и формат сохранённой настройки культуры.
Миграция пользовательских настроек не требуется.

Задача не включает загрузку переводов после установки, внешний изменяемый
JSON, наблюдение за файлами, сервер переводов, каталог тем и изменение
логики `SetCultureAsync`. Другие пункты аудита, включая общий потоковый
контракт сервиса, остаются самостоятельными задачами.

## 🔎 2. Проверенная исходная точка до реализации

- [LocalizationService.cs](../../../KID.WPF.IDE/Services/Localization/LocalizationService.cs)
  читает `Language_Count` и пары индексированных строк, строит ключ
  `Language_{EnglishName}` и хранит список с двумя словарями.
- Старый `Resources/AvailableLanguage.resx` содержал три записи в порядке
  `en-US`, `ru-RU`, `uk-UA`; при реализации файл удалён.
- Пустой или нечисловой счётчик даёт пустой каталог. Ноль и отрицательное
  число также не дают записей; заниженное положительное число скрывает
  часть языков, завышенное приводит к пропуску отсутствующих записей.
- Неполные записи пропускаются без предупреждения. Дубликаты перезаписывают
  соответствия в словарях, сохраняя дубли в списке. Частичный результат
  после исключения также может попасть в кэш.
- `GetAvailableLanguages()` возвращает внутренний `List<string>` под типом
  `IEnumerable<string>`, поэтому вызывающий код может изменить его через приведение.
- [MenuViewModel.cs](../../../KID.WPF.IDE/ViewModels/MenuViewModel.cs)
  сейчас копирует элементы в `ObservableCollection<string>`.
  [MenuView.xaml](../../../KID.WPF.IDE/Views/MenuView.xaml) использует
  ключи для подписей, команды выбора и галочки текущего языка.
- Текущие три записи корректны; названия всех трёх языков присутствуют
  во всех трёх переводах. Воспроизведённого пользовательского дефекта LOC-09 нет.
- Проект использует .NET 10 и `System.Text.Json`; добавлять JSON-пакет не требуется.
- В [AssemblyInfo.cs](../../../KID.WPF.IDE/Properties/AssemblyInfo.cs)
  уже есть `InternalsVisibleTo("KID.Tests")`: проверяемые внутренние методы
  не нужно делать публичными ради тестов.

Это результаты чтения исходников и ресурсов при подготовке плана.
Результаты сборки и тестов из аудита не считаются проверками будущей реализации.

## 📄 3. Формат и подключение JSON

Новый файл: `KID.WPF.IDE/Resources/AvailableLanguages.json`.

```json
[
  {
    "cultureCode": "en-US",
    "displayNameKey": "Language_English"
  },
  {
    "cultureCode": "ru-RU",
    "displayNameKey": "Language_Russian"
  },
  {
    "cultureCode": "uk-UA",
    "displayNameKey": "Language_Ukrainian"
  }
]
```

Порядок элементов определяет порядок пунктов меню. Версия схемы, отдельное
поле количества и настройки текущего языка этому файлу не нужны.

В `KID.WPF.IDE.csproj` явно задать подключение:

```xml
<None Remove="Resources\AvailableLanguages.json" />
<EmbeddedResource Include="Resources\AvailableLanguages.json"
                  LogicalName="KID.Resources.AvailableLanguages.json" />
```

Читать ресурс из сборки `LocalizationService` по этому логическому имени
через `GetManifestResourceStream`. Для JSON не использовать WPF build action
`Resource`, относительный путь файловой системы или `CopyToOutputDirectory`.
Проверить присутствие ресурса именно в собранной основной сборке.

## 🧩 4. Структура кода и контракт

### 4.1. Внутренняя модель и снимок

Добавить небольшой внутренний `LanguageCatalog` в подсистему локализации.
В том же файле допустимо определить внутреннюю запись `LanguageDefinition`
с `CultureCode` и `DisplayNameKey`. Публичную модель и новый DI-сервис
для этого каталога не вводить.

Снимок содержит:

- неизменяемые записи языков и упорядоченные ключи — `ImmutableArray`;
- соответствия ключ → культура и культура → ключ — `FrozenDictionary`;
- сравнение ключей словарей — `StringComparer.OrdinalIgnoreCase`, как сейчас.

Коллекции создаются из локальных проверенных данных. Изменяемые списки,
массивы и словари, используемые во время чтения, наружу не передаются.
Один только тип `IReadOnlyList` поверх доступного для изменения списка
не считается защитой.

### 4.2. Подключение к LocalizationService

- Заменить три независимо заполняемых поля кэша одним
  `Lazy<LanguageCatalog>` с однократным созданием снимка.
- Удалить `_availableLanguageResourceManager` и старый `EnsureLanguageMappings()`.
- Оставить сигнатуры `GetAvailableLanguages()`,
  `GetCultureCodeByLanguageKey()` и `GetLanguageKeyByCultureCode()`.
- Сохранить возврат пустой строки для неизвестного ключа или культуры.
- Не менять публичный конструктор сервиса, регистрацию в DI,
  `GetString`, сохранение настроек и уведомления о смене культуры.
- `GetAvailableLanguages()` возвращает неизменяемые ключи снимка через
  существующий `IEnumerable<string>`.

Для тестов предусмотреть внутреннюю фабрику с подменяемым источником
потока и проверкой ресурсов. Внешний контейнер зависимостей и production API
ради имитации ошибочного JSON не расширять.

Однократная публикация снимка защищает только инициализацию каталога.
Она не является исправлением общего потокового контракта из LOC-08.

## 🔍 5. Правила проверки

### 5.1. Структура JSON

1. Корень — непустой массив; `null`, пустой массив и другой тип корня ошибочны.
2. Каждый элемент — объект с двумя обязательными непустыми строками.
3. Имена свойств — ровно `cultureCode` и `displayNameKey`.
   Неизвестные свойства отклоняются, чтобы опечатка не превращалась в игнорируемое поле.
4. Использовать строгий JSON без комментариев и завершающих запятых.
5. Настройки `JsonSerializerOptions` создать один раз и переиспользовать.

### 5.2. Значения и уникальность

1. Отклонять пустые значения и значения с пробелами по краям.
2. Разрешать код через `CultureInfo.GetCultureInfo`, использовать каноническое
   имя культуры для хранения и проверки дублей.
3. Отклонять повторяющиеся культуры и ключи названий, включая различия
   только в регистре. Не перезаписывать предыдущую запись и не оставлять
   «первое подходящее» значение.
4. Проверять существование ключа с точным регистром: сравнение при поиске
   соответствий не должно скрывать ошибку имени ресурса.

Успешный `GetCultureInfo` подтверждает распознавание кода платформой,
но сам по себе не подтверждает наличие перевода KID.

### 5.3. Соответствие ресурсам

- Для каждой культуры из JSON должен существовать её собственный набор
  `Strings` в собранном приложении.
- Проверять набор через `ResourceManager.GetResourceSet` с
  `tryParents: false`, а строки — непосредственно через `ResourceSet`.
- Дополнительно сверять `Metadata_CultureCode` с запрошенной культурой,
  чтобы родительский или ранее закэшированный fallback не подтвердил
  существование нужного перевода ошибочно.
- Полученные из общего `ResourceManager` наборы не освобождать отдельно:
  ими управляет сам менеджер, который продолжает обслуживать `GetString`.
- В каждом языке каталога должны существовать непустые значения всех
  `displayNameKey` этого каталога: для текущих ресурсов это девять проверок.
- Для аварийной записи должны присутствовать английские ресурсы и
  `Language_English`; это отдельно закрепляется тестом поставки.

Не проверять наличие перевода через обычный `LocalizationService.GetString()`:
он может вернуть английский fallback. Полная проверка всех строк интерфейса
выходит за границы LOC-09; здесь проверяется согласованность самого каталога.

## 🛟 6. Ошибки, fallback и кэш

Принятая политика: ошибка любой записи делает основной каталог
недействительным целиком. Молча пропускать строки и публиковать частичный
результат нельзя.

При отсутствии встроенного JSON, ошибке чтения, десериализации или проверки:

1. Записать одно предупреждение через существующий
   `DiagnosticEventIds.LocalizationFallback`. Указать имя ресурса и причину;
   для ошибки записи — индекс, поле и конфликтующее значение, если применимо.
2. Создать неизменяемый аварийный каталог из одной записи:
   `en-US / Language_English`.
3. Опубликовать его как согласованный снимок списка и обоих словарей.

Аварийная запись — единственное исключение из хранения
перечня в JSON. Это не второй полный список поддерживаемых языков в C#;
читать резерв из того же ошибочного JSON бессмысленно.

В fallback не переключать текущую культуру автоматически и не переписывать
настройки. Он восстанавливает доступную команду выбора английского языка.
Восстановление отсутствующих английских ресурсов — отдельная проблема
поставки, которую этот каталог решить не может.

Кэшировать можно успешно проверенный основной снимок или намеренно
созданный аварийный. Пустой либо частично прочитанный каталог не публикуется.
При повторных обращениях не повторять чтение и предупреждение: встроенный
ресурс не изменяется в рамках запуска. Ожидаемые ошибки загрузки и данных
обрабатываются на этой границе; фатальные ошибки процесса не маскируются
общим `catch` ради fallback.

## 🧪 9. Проверки реализации

### 9.1. Автоматизированные сценарии

- Реальный встроенный JSON загружается без fallback и сохраняет
  порядок `en-US`, `ru-RU`, `uk-UA` с прежними ключами.
- JSON синтаксически повреждён; корень другого типа; `null`; пустой массив;
  `null` вместо записи; поле отсутствует, пустое, неверного типа или с опечаткой.
- Дубликаты кода культуры и ключа, включая различия регистра, отклоняются.
  Ошибка после корректной первой записи также даёт целый аварийный каталог.
- Нераспознаваемая культура, отсутствующий собственный перевод,
  неправильные метаданные, отсутствующая или пустая подпись отклоняются.
- Наличие строки только в английском fallback не подтверждает её наличие
  в другой культуре; использовать изолированный тестовый источник ресурсов.
- Отсутствие потока и ошибка чтения дают одну аварийную запись и одну
  диагностическую запись; повторные вызовы повторно источник не читают.
- Список и оба направления поиска согласованы при штатной загрузке и fallback.
  Неизвестные значения по-прежнему дают пустую строку.
- Попытка изменения выданной коллекции не меняет последующие выдачи и словари.
- Тест поставки проверяет в собранных ресурсах все пары
  «культура интерфейса × displayNameKey», а также доступность английского резерва.

Тест поставки должен отличать успешный основной каталог от аварийного:
одного утверждения «список не пуст» недостаточно.

### 9.3. Ручная проверка меню

1. Запустить собранное приложение и проверить три пункта в прежнем порядке.
2. Переключиться последовательно на каждый язык: проверить подписи,
   галочку и фактически выбранную культуру.
3. Перезапустить приложение после выбора языка и проверить сохранение настройки.
4. Убедиться, что рядом с приложением не требуется внешний JSON-файл.

Известные дефекты обновления UI из других пунктов аудита учитывать отдельно:
проверка каталога не подтверждает их исправление.

## 📋 11. Фактические результаты реализации — 2026-10-24

Все изменения из § 7 внесены. Основной каталог находится только в JSON;
