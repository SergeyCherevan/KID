# 🔄 План 02: единое состояние UI и контракт переключения языка

**Статус:** `proposed`. **Дата:** 2026-10-24.
**Пункты аудита:** LOC-03, LOC-08; регрессии LOC-04 и часть LOC-05.
**Навигация:** [карта планов](LOCALIZATION_AUDIT_CLOSURE_2026-10-24.md).
**Зависимости:** после плана 01; контракт используется планами 03–05.

## 🔎 Проверенная исходная точка

`MenuViewModel.SelectedCultureCode` читает `Settings.UILanguage`.
`SelectedLanguageKey` вычисляется из этого значения. На `CultureChanged`
публикуются только `SelectedLanguageKey` и `ExecutionStatusText`, а триггер
`SelectedCultureCode` — по `UILanguageSettingsChanged` после записи.
`MenuView.xaml` использует этот триггер для подписей тем и языков.

`LocalizationService` получает сохранение через `IServiceProvider`.
`ILocalizationService` не наследует `INotifyPropertyChanged`, хотя XAML
использует уведомления реализации. Markup extension и два конвертера
разрешают зависимости через `App.ServiceProvider`.

Проверенная цепочка: `WindowConfigurationService → IFileService →
ILocalizationService`; дополнительно конфигурация напрямую читает каталог
через `ILocalizationService`. Прямое внедрение конфигурации в конструктор
локализации создаст цикл. Крупная переделка файлового сервиса не требуется.

## 🎯 Предлагаемое решение

Разделить чтение строк/состояния и команду переключения:

- `ILocalizationService : INotifyPropertyChanged` — lookup, `CurrentCulture`,
  каталог, `CultureChanged`. Текущая культура означает применённый язык UI.
- Новый `ILanguageSelectionService.SetCultureAsync` — применить канонический
  язык на UI-потоке, инициировать сохранение и ожидать его результат.
- `LocalizationService` больше не получает `IServiceProvider` и не сохраняет
  настройки. Узкий внутренний `ApplyCulture` меняет его состояние и публикует
  уведомления; использовать его может координатор, а не ViewModel.
- Новый `LanguageSelectionService` зависит от конкретного singleton
  `LocalizationService`, `IWindowConfigurationService` и `JoinableTaskFactory`.
  Интерфейс чтения и конкретный сервис указывают на один экземпляр.

Схема конструирования: `LanguageSelectionService → LocalizationService` и
`LanguageSelectionService → WindowConfigurationService → LocalizationService`.
У `LocalizationService` нет обратной зависимости, цикл отсутствует.

Перенос `SetCultureAsync` между интерфейсами — осознанное внутреннее изменение
контракта приложения. Все production-вызовы, тесты, заглушки и описание API
переводятся в одном изменении. Не оставлять старый service locator как скрытый
совместимый путь; внешняя публичная совместимость KID.Library не затрагивается.

## 📜 Контракт событий, потока и записи

1. `SelectedCultureCode` и галочка берутся из текущей культуры сервиса,
   а не из подтверждения дисковой записи. Статус сохранения — отдельное событие
   конфигурации; нового пользовательского индикатора этот план не требует.
2. Валидация до изменения состояния. Изменения культуры и WPF-уведомления
   выполняются на UI-потоке. Фоновый вызов координатора переключается туда
   через JTF; порядок запросов определяется их принятием UI-диспетчером.
3. Для изменённого языка: обновить состояние → `PropertyChanged(CurrentCulture)`
   и зависимые UI-свойства → `CultureChanged` → ожидать результат записи.
   Запись может быть инициирована до события, но её успех не условие события.
4. Сохранение запускается без удержания блокировки/очереди UI на всё время IO.
   Пока первая запись ожидается, второй принятый запрос может изменить UI.
   Существующая FIFO-очередь конфигурации и ревизии остаются ответственными
   за итоговый записанный язык; старое завершение не откатывает новый UI.
5. Повтор того же языка не публикует ложную смену культуры, но повторяет
   неуспешное сохранение. Ошибка относится к задаче соответствующего запроса
   и проходит через существующий error handler; UI остаётся на применённом языке.
6. Назначение ambient-культуры внутри async-метода не обещает смены культуры
   вызывающего контекста. Потребители языка операции используют явный снимок
   по плану 03; глобальные `DefaultThreadCurrentCulture` не являются решением.

## 🪜 Шаги

1. Сначала исправить `SelectedCultureCode` и уведомления, закрепить сценарий
   задержанной/неудачной записи тестом реальной ViewModel.
2. Выделить координатор без изменения гарантий плана 01. Обновить все вызовы
   `SetCultureAsync`, включая startup и тестовые фабрики; повторно проверить DI.
3. Сделать `INotifyPropertyChanged` обязательной частью интерфейса.
   Уведомления передавать WPF-адаптеру; при подписках определить lifetime
   и отписку, не создавать удерживаемые singleton-сервисом закрытые окна.
4. Убрать повторный глобальный поиск сервиса из преобразований конвертеров.
   Сохранить используемые XAML-ключи и понятный fallback при недоступной
   composition boundary; не расширять рефакторинг на весь проект DI.
5. Закрепить очередь принятых запросов и семантику ошибок/повторов
   управляемыми барьерами задач, без `Thread.Sleep`.

## 🧪 Приёмка

- Уже созданные элементы тем/языков, галочка, заголовок и статус обновляются
  до разблокирования сохранения; ошибка IO не оставляет старые подписи.
- Startup с уже каноническими загруженными настройками обновляет всё меню,
  даже когда конфигурация не отправляет событие повторного сохранения.
- Запрос с worker публикует WPF-уведомления на UI-потоке; два быстрых выбора
  имеют определённый конечный UI и итоговую запись. Первый поздний success
  или failure не меняет уже применённый второй язык.
- Повтор того же языка после IOException работает; ложных событий смены нет.
- Привязка обновляется с реализацией только по объявленному интерфейсу;
  адаптер и конвертеры проверяются без запуска полного приложения.
- Все сценарии плана 01 и тесты культуры скрипта сохранены.
