# 🚑 План 04: собственные ошибки KID и независимые crash-сообщения

**Статус:** `proposed`. **Дата:** 2026-10-24.
**Пункты аудита:** LOC-06 и соответствующая часть LOC-05.
**Навигация:** [карта планов](LOCALIZATION_AUDIT_CLOSURE_2026-10-24.md).
**Зависимости:** после плана 02; проверки выпуска — в плане 06.

## 🔎 Проверенная исходная точка

`App.BuildCrashMessage` всегда формирует русский текст. Он вызывается
при ошибке startup и необработанном исключении UI, когда DI/RESX уже могут
не работать. Аварийный перевод нельзя строить только на обычном сервисе.

`Music.Advanced.cs` выбрасывает `FileNotFoundException` с русским сообщением.
`CollectibleCodeRunningInstance.ClassifyUserException` сводит runtime-ошибку
к `exception.Message` и `StackTrace`; `ExecutionResult` не несёт типа/кода ошибки.
`MenuViewModel.ReportExecutionResult` добавляет оболочку `Error_Execution`,
поэтому UI не может отличить собственную переводимую ошибку KID от произвольной.

`UserProgramLoadContext` разрешает зависимости через default context:
KID.Library имеет общую идентичность типов с host. Но произвольные объекты,
исключения и аргументы из пользовательского ALC нельзя удерживать в результате
запуска — это может помешать выгрузке.

## 🎯 Политика сообщений

1. Собственные сообщения, предназначенные пользователю KID, переводятся
   по стабильному коду и параметрам. Первый обязательный случай — отсутствующий
   музыкальный файл; остальные пользовательские ошибки включаются по инвентаризации.
2. Внутренние инварианты, stack traces, произвольные .NET/сторонние исключения
   и текст пользовательской программы остаются оригинальными. Для них UI
   показывает локализованную оболочку и явно описанный технический текст.
3. Технические тип, сообщение, стек и inner exception не заменяются переводом
   в диагностике. Локализованное сообщение не используется для классификации.
4. KID.Library передаёт данные, но не обращается к WPF, DI или RESX приложения.
5. Новые ошибки не меняют семантику Stop, cleanup, ошибок IO и выгрузки ALC.

## 🛟 Независимая аварийная локализация

Добавить небольшой `EmergencyLocalization` с фиксированными строками
`en / ru / uk`: неожиданное завершение, идентификатор, неизвестный идентификатор,
путь отчёта. Этот код не использует DI, ResourceManager, чтение settings,
сеть или блокирующее ожидание. Конечный гарантированный fallback — английский.

До применения настроек язык определяется из системной UI-культуры по
поддерживаемым языкам с безопасным `en` fallback. После применения сохраняется
последний выбранный канонический код в простом атомарно читаемом снимке.
Координатор плана 02 обновляет снимок при применении, независимо от записи
на диск. Сам crash boundary только читает готовое значение.

`App` передаёт `CrashReportInfo` чистому formatter: варианты с отчётом,
без пути и без идентификатора не вызывают новой ошибки. Не переводить
значения CrashId и пути. Сбой показа диалога сохраняет нынешний shutdown/logging.
Строки аварийного formatter проверяются отдельно от обычных RESX.

## 🧩 Структурированные библиотечные ошибки

Предлагаемый минимальный контракт:

- `KidErrorCode` и `KidErrorDescriptor` в KID.Library: стабильный код и
  неизменяемые разрешённые параметры простых типов. Для Music — исходный путь.
- `IKidUserFacingError` для исключений, имеющих такое описание.
- `MusicFileNotFoundException : FileNotFoundException` с этим контрактом:
  сохраняет совместимость `catch (FileNotFoundException)` и `FileName`;
  техническое сообщение допустимо на фиксированном английском языке.

На границе runtime распознать только известный контракт и скопировать
разрешённые данные в host-owned результат. В `ExecutionResult` добавить
необязательное структурированное описание. `ErrorMessage` / технические
сведения сохраняются для диагностики и fallback неизвестного кода.
Не хранить сам exception, `Type`, объект пользователя или произвольный
`object[]` из ALC в терминальном результате.

UI-mapper переводит известный код в RESX-ключ и аргументы; неизвестный код
возвращает исходный технический текст под локализованной оболочкой.
Текст собственных runtime-ошибок формируется на языке UI **при отображении**,
поскольку результат несёт данные; это отличается от снимка компиляции из плана 03.

## 🪜 Реализация и проверки

1. Инвентаризировать собственные пользовательские строки в C#/XAML и Music;
   для каждой записать «переводимый код» либо конкретную диагностическую роль.
   Не включать комментарии, имена API и произвольные сообщения пользовательского кода.
2. Реализовать аварийный formatter и тесты всех трёх языков: DI отсутствует,
   RESX недоступны, неподдерживаемый код, null report, отсутствующий путь/CrashId.
3. Реализовать один сквозной Music-код, затем остальные подтверждённые собственные
   пользовательские ошибки из инвентаризации тем же механизмом.
4. Проверить отсутствие музыкального файла через настоящий execution pipeline
   на трёх языках: локализованный смысл, исходный путь, оригинальная диагностика.
5. Проверить неизвестную ошибку/код, пользовательское русское или английское
   исключение, вложенное исключение и отмену: текст не переводится по догадке,
   Stop не превращается в ошибку, диагностические данные сохраняются.
6. Проверить выгрузку пользовательского ALC после собственного и неизвестного
   исключения. Не создавать статические кэши исключений/типов пользователя.
7. Реальный fatal-сценарий проверять в отдельном тестовом процессе; чистые тесты
   formatter не доказывают показ MessageBox и завершение полного приложения.
