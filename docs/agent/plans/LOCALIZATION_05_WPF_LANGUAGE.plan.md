# ♿ План 05: язык WPF, текстовые области и доступность

**Статус:** `proposed`. **Дата:** 2026-10-24.
**Пункты аудита:** LOC-07 и соответствующая часть LOC-05.
**Навигация:** [карта планов](LOCALIZATION_AUDIT_CLOSURE_2026-10-24.md).
**Зависимости:** после единого состояния и WPF-адаптера плана 02.

## 🔎 Проверенная исходная точка

В `MainWindow.xaml` и просмотренных Views не установлен динамический
`Language` / `xml:lang`. Аудит наблюдал default metadata `TextBlock.Language`
как `en-us`; конкретную ошибку Narrator или визуальный дефект не воспроизводил.
`CurrentCulture` сервиса и язык содержимого редактора/консоли — разные понятия.

## 🎯 Предлагаемая политика

- Корень интерфейса получает `FrameworkElement.Language` из текущего
  канонического языка локализации. Преобразование в `XmlLanguage` явное,
  изменение динамическое, источник не связан с сохранением настроек.
- Наследуемые подписи UI получают тот же язык. Для `Popup`, `ContextMenu`
  и `ToolTip` отдельно проверить фактическое наследование и при разрыве
  дерева передать источник явно; не полагаться на наличие предка Window.
- Пользовательский C#-код и консоль содержат произвольные языки.
  `ProgrammingLanguage = CSharp` не означает человеческий язык комментариев
  или строк. Предлагаемая начальная политика — сохранять действующее поведение
  содержимого этих двух областей через явную границу локального `Language`,
  а не автоматически менять его при смене языка оболочки. Значение зафиксировать
  после измерения текущего поведения в тестовой среде; если оно `en-US`,
  закрепить `en-US` как технический default, не утверждая, что весь текст английский.
- Для пользовательского текста не обещать автоматическое определение языка
  или правильное произношение смешанных фрагментов. Доступные имена/подсказки
  самих контролов относятся к UI и переводятся независимо от содержимого.
- Все текущие языки LTR. RTL и общая переделка accessibility вне LOC-07.

Изменения наследуемого `Language` могут повлиять на форматирование WPF Binding.
Для существующих числовых значений проверить чтение/ввод; технический парсинг
настроек и пользовательского C# не должен зависеть от нового свойства корня.
Полная политика provider собственных `string.Format` остаётся в R15.

он не обеспечивает дальнейшее переключение. Не менять глобальные культуры
потоков как замену `FrameworkElement.Language`.

## 🪜 Шаги

1. Снять исходные `Language` у Window, TextBlock, элементов меню,
   редактора, консоли и popup-контента; отдельно проверить UI Automation culture.
2. Подключить converter и динамическую привязку корня к применённой культуре.
3. Проверить наследование в обычном дереве и popup-границах; исправлять только
   найденные разрывы. Для повторно открываемых меню проверить свежий и уже
   созданный контейнер после смены языка.
4. Закрепить локальные границы пользовательского текста и описать их смысл.
   Проверить, что доступные названия самих редактора/консоли остаются локализованными.
5. Пройти ввод/отображение размеров шрифта и других WPF-привязок чисел,
   чтобы изменение `Language` не повредило штатные команды.
6. Выполнить тесты UI Automation и ручную проверку Narrator на трёх языках.

## 🧪 Доказательства доступности

- Для каждого `en / ru / uk` записать фактические `XmlLanguage` корня,
  наследуемого текста, меню и отделённых областей до и после переключения.
- UI Automation: проверить доступную culture-информацию и локализованные
  имена/подсказки там, где provider их публикует. Если property не поддержан
  конкретным control/provider, зафиксировать это вместо выдуманного значения.
- Narrator: заголовок, File/View, список языков/тем, статус и подсказки;
  отдельно редактор со смешанными комментариями и консоль с текстом программы.
- Записать версию Windows, выбранный голос и наличие языковых компонентов.
  При отсутствии голоса нужного языка проверка произношения остаётся открытой;
  установка голоса не подменяется утверждением об успешной приёмке.
- Не называть изменение `Language` доказательством исправленного произношения:
  нужны наблюдения соответствующего диктора. Общий DPI/темы smoke — в плане 06.
