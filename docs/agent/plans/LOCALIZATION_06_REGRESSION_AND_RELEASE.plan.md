# 🧪 План 06: постоянные регрессии и приёмка опубликованной локализации

**Статус:** `proposed`. **Дата:** 2026-10-24.
**Пункты аудита:** LOC-05; итоговые доказательства LOC-01–LOC-09 и все
отмеченные аудитом пробелы проверки локализации.
**Навигация:** [карта планов](LOCALIZATION_AUDIT_CLOSURE_2026-10-24.md).
**Зависимости:** проверки добавляются вместе с исправлениями; итог после планов 01–05.

## 🔎 Исходная точка и границы доказательств

Фраза исходного аудита об одном прямом тесте описывает старый снимок.
Сейчас `LocalizationServiceTests`, `LanguageCatalogTests`,
`LanguageCatalogResourceTests`, тесты конфигурации и культуры скрипта уже
содержат значительную часть сценариев. Сначала сохранить их и выявить
конкретные пробелы. Не переписывать работающие проверки только ради новых имён.

По результатам перехода культур в существующем плане есть исторические
сборка, полный набор и publish. Это не доказательство будущего состояния
после шести новых планов. Разовые probe из Temp не являются постоянным барьером.

## 🧱 Три уровня проверки

1. **Обычный набор тестов:** данные RESX/JSON, поведение lookup,
   конфигурации, координатора, компилятора, mapper ошибок и WPF-адаптера.
2. **Проверка публикации:** отдельный чистый каталог, реальная структура
   ресурсов и запуск probe в новом процессе из этого артефакта.
3. **Ручная приёмка:** полный UI, DPI/темы, startup/перезапуск, accessibility,
   лингвистическая проверка и запуск на чистой Windows.

Прохождение одного уровня не подменяет остальные. R15 имеет отдельный
отложенный набор; его отсутствие не мешает завершить LOC-01–LOC-09.

## 🔤 Данные и шаблоны в обычном тестовом запуске

- Прочитать исходные `Strings.resx`, `Strings.ru.resx`, `Strings.uk.resx`:
  одинаковые имена ключей с точным регистром, отсутствие дубликатов и пустых
  значений. Не закреплять число `60` как вечное — новые сообщения плана 04
  законно расширяют каталог. `Metadata_CultureCode` ожидаемо различается.
- Проверить все ключи в собранных собственных resource sets, не только названия
  языков/тем. `tryParents: false` и точные метаданные обязательны: fallback
  не должен скрывать потерянный перевод в проверке целостности поставки.
- Валидировать составные шаблоны через `CompositeFormat.Parse`; сравнить
  наборы индексов аргументов между языками. Учесть escaped braces, повторы,
  alignment, format specifiers и переупорядочивание аргументов переводчиком.
  Проверка одних регулярных выражений без разбора формата недостаточна.
- Проверять форматируемые ключи с аргументами и реальным `GetString`;
  плохой шаблон обнаруживается как ошибка теста, а не прячется за `[ключ]`.
- Сверить используемые в C#/XAML постоянные ключи и явные динамические
  источники: JSON языков, определения тем, кодовые mapper ошибок, статусы.
  Не считать `Language_Count` / `Theme_Count` из других resource sets
  пропусками в Strings; legacy aliases учитывать явно.
- Для проверки исходных XML закрепить явное расположение/copy входных
  данных в тестовом проекте. Тест не должен случайно читать старую рабочую
  директорию или требовать абсолютного пути машины автора.

## 📦 Проверка publish-артефакта

1. Создать новый временный каталог; выполнить Release publish. Не использовать
   старый `bin`, где остатки `ru-RU` / `uk-UA` могут скрыть ошибку упаковки.
2. Проверить базовые `KID.Resources.Strings.resources`, английский neutral attribute,
   встроенный JSON, собственные KID satellite assemblies `ru` и `uk`, каталоги
   тем/шрифтов. Проверять имя assembly, не любую похожую папку зависимости.
3. В новом процессе загрузить именно указанную опубликованную сборку,
   вывести её путь и commit/version. Проверить каталог, реальные lookup всех
   ключей и шаблонов, три языка и региональные алиасы. Запретить незаметный
   fallback resolver в исходные `bin`/NuGet-пути при проверке собственных ресурсов.
4. В отдельной копии удалить ru либо uk satellite и повторить в новом процессе:
   основной английский набор, аварийный каталог и технический фильтр работают.
   Исходную публикацию не изменять. Отдельно проверить отсутствие перевода Roslyn
   по политике плана 03; не смешивать её с повреждением собственных ресурсов KID.
5. Во временном профиле загрузить старые/неподдерживаемые настройки, сохранить,
   запустить второй процесс/экземпляр и подтвердить результат. Пользовательский
   рабочий профиль для повреждённых настроек и fault injection не использовать.
6. На чистой Windows/VM без Visual Studio и SDK выполнить запуск опубликованного
   приложения с необходимым Desktop Runtime либо выбранной self-contained
   поставкой. Проверить язык, Open/Save и компиляцию. Записать условия установки;
   локальный publish без такого запуска не закрывает этот пробел аудита.

Скрипт работает только со своими явно созданными временными каталогами;
повреждение/удаление тестовых файлов не должно касаться исходной публикации
или рабочих настроек. При недоступности среды проверка остаётся открытой.

## 🖥️ Ручная матрица

Базовый проход: **3 языка × 4 темы × 3 масштаба = 36 сочетаний**.
Темы: VS2022 Light/Dark, VS2026 Light/Dark. DPI: 100%, 150%, 200%.
В каждом сочетании проверить узкое и обычное окно: заголовок, меню,
длинные подписи, списки языков/тем и статус; записать обрезание/наложение.

Дополнительные сценарии для каждого языка:

- Сначала создать/открыть подменю, затем сменить язык; проверить уже созданные
  элементы, контекстные меню, tooltip и повторное открытие popup.
- Startup со старым региональным кодом и уже нормализованным кодом,
  смена языка, закрытие и повторный запуск; галочка соответствует UI.
- Открытие, Save As, отмена диалога и ошибка IO; длинные локализованные
  сообщения компиляции/исполнения и собственная ошибка Music.
- Контролируемые задержка/ошибка записи языка и повтор. Сначала использовать
  тестовый стенд/временный профиль, затем подтвердить видимые обновления UI.
- Проверка UI Automation/Narrator по инструкции плана 05.
- Лингвистическая приёмка человеком, владеющим соответствующим языком:
  смысл, терминология, естественность, placeholders и технические фильтры.
  Синтаксическая целостность RESX не считается языковой экспертизой.

Отдельно исследовать два пробела исходного аудита:

- **Нативные диалоги Windows:** записать язык системных кнопок и язык наших
  подписей/фильтра. Несовпадение языка ОС не называть автоматически дефектом
  перевода KID; зафиксировать зависимость от Windows и доступные настройки.
- **RoslynPad:** проверить inline diagnostics, tooltip и completion на трёх
  языках. Отделить собственные строки KID от ресурсов зависимости. Если есть
  поддержанный способ передать культуру, применить его в рамках контракта
  плана 03; иначе документировать английский fallback и конкретный предел API.

Каждый обнаруженный собственный дефект возвращается в соответствующий план
и исправляется до приёмки. Ограничение ОС/зависимости записывается с доказательством;
оно не скрывает ошибку собственного провайдера KID.

## ▶️ Команды после реализации

Из корня репозитория, после доступного restore:

```powershell
dotnet build KID.sln -c Release --nologo
dotnet KID.Tests/bin/Release/net10.0-windows/KID.Tests.dll -namespace KID.Tests.Localization -noLogo -noColor
dotnet KID.Tests/bin/Release/net10.0-windows/KID.Tests.dll -noLogo -noColor
pwsh -NoProfile -File scripts/validation/Test-LocalizationPublish.ps1
git diff --check
```

Это будущие команды, а не результаты подготовки планов. Точный интерфейс
нового publish-скрипта закрепить при реализации; без обязательных параметров
он создаёт собственную временную публикацию. Встроенные в тесты барьеры
синхронизации не должны зависеть от `Thread.Sleep`.
