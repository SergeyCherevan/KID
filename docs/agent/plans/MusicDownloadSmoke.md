# 🎧 Ручная проверка R02: URL-аудио, лимит и Stop

Подготовка не меняет settings/session KID и не удаляет существующие пользовательские файлы.
Проверка использует локальный HTTP-сервер и синтезированный тихий WAV-тон 440 Гц длительностью 3 секунды.
Это проверка реального NAudio/WAV и Music lifecycle, без внешнего сайта. MP3/другие кодеки и HTTPS
нужно проверять отдельно на своих файлах и адресах.

## 1. Запустить сервер

Используй KID, собранный после R02. Сервер — отдельное однофайловое ASP.NET Core-приложение:
в начале `.cs` указано `#:sdk Microsoft.NET.Sdk.Web`, маршруты объявлены через `app.MapGet`.
Для запуска нужен .NET 10 SDK (в текущей среде установлен 10.0.401). Запусти его из PowerShell
в корне репозитория:

```powershell
dotnet run --file .\scripts\manual-checks\Serve-MusicDownloadFixture.cs
```

Сервер слушает только `127.0.0.1:8765`, не создаёт файлов и не раздаёт файлы компьютера.
Оставь терминал открытым. В начале должны появиться адрес и размер WAV **264644 байта**.
Если порт занят, добавь `-- --port 8766` к команде запуска и поменяй `root` в C#-примере на этот порт.
Сервер предоставляет обычный ответ, chunked без Content-Length, медленную загрузку (~26 секунд) и 404.

Самопроверка сервера выполняется на том же порту. Останови работающий сервер, затем запусти:

```powershell
dotnet run --file .\scripts\manual-checks\Serve-MusicDownloadFixture.cs -- --self-check
```

Ожидаемый итог: `Fixture self-check passed`. Для другого порта добавь `--port 8766` после `--self-check`.
Этот сервер запускается через SDK в отдельном терминале; C#-пример с Music запускается в KID.

## 2. Подготовить пример и наблюдение за файлами

Открой соседний [пример MusicDownloadSmoke.cs](../../../scripts/manual-checks/MusicDownloadSmoke.cs) в редакторе KID и нажми Run.
В консоли появится меню: введи номер сценария и нажми Enter. После завершения сценария меню появляется снова;
`0` завершает проверку. Некорректный ввод повторяет запрос. Код между сценариями менять не требуется.
Не запускай файл через dotnet: Music требует execution-сессию KID и её graphics runtime.
Звук тихий, но перед проверкой выбери комфортную громкость устройства.

В другом PowerShell сохрани список уже существующих временных файлов:

```powershell
$musicSmokeTemp = [IO.Path]::GetTempPath()
$musicSmokeBefore = @(Get-ChildItem -LiteralPath $musicSmokeTemp -Filter 'kid-audio-*.tmp' -File |
    Select-Object -ExpandProperty FullName)
```

Пример печатает TEMP процесса KID. Если он отличается от PowerShell, используй этот путь
в `$musicSmokeTemp` и заново сохрани baseline. Для наблюдения во время медленной загрузки выполняй:

```powershell
Get-ChildItem -LiteralPath $musicSmokeTemp -Filter 'kid-audio-*.tmp' -File |
    Where-Object { $_.FullName -notin $musicSmokeBefore } |
    Select-Object Name, Length, LastWriteTime
```

Во время сценария 6 должен появиться файл, размер которого постепенно растёт. Буферизация может
задерживать изменения видимой длины; один снимок с длиной 0 не означает, что загрузка остановилась.
После завершения или Stop эта команда не должна показывать новых оставшихся файлов.
Не удаляй старые файлы из baseline. Используй один экземпляр KID, чтобы не смешивать результаты.

## 3. Проверить успешное воспроизведение и Stop

В одном запуске выбери сначала **1, 2, 7, 10, 5, 11, 12**. Сценарии **6 и 8** проверяют кнопку Stop
самого KID и завершают весь запуск, поэтому после каждого из них скрипт нужно запустить снова.

1. **Без лимита:** слышен трёхсекундный тон, затем `OK`; новых temp-файлов после завершения нет.
2. **Ровно лимит:** то же при `maxDownloadBytes = 264644`; пограничный размер допустим.
7. **Отложенный запуск:** в течение трёх секунд после `SoundLoad` HTTP-запроса нет;
   запрос появляется после `SoundPlay`, затем звук и `OK`.
10. **Chunked с null:** трёхсекундный тон и `OK`, несмотря на отсутствие Content-Length.
5. **SoundStop:** медленная загрузка прерывается примерно через 1,5 секунды, повторный Stop не зависает;
   затем обычный URL проигрывается в той же сессии. Сервер может написать `client disconnected` — это ожидаемо.
11. **Ручной SoundStop при загрузке:** нажми Enter в консоли через 2–5 секунд. Частичный файл удалён,
    звук не начинается, появляется меню. Выбери 1, чтобы проверить новый звук в той же сессии.
12. **Ручной SoundStop при playback:** дождись повторяющегося тона и нажми Enter в консоли.
    Звук прекращается, файл удалён, появляется меню. Выбери 1, чтобы проверить следующий звук.
6. **Stop кнопкой KID при скачивании:** нажми Stop через 2–5 секунд, пока звук ещё не начался.
   Загрузка завершается, частичный файл удалён. Затем запусти сценарий 1: звук должен работать снова.
8. **Stop во время воспроизведения:** дождись слышимого повторяющегося тона и нажми Stop в KID.
   Звук прекращается, временный файл удалён. Затем сценарий 1 должен снова работать.

Для сценариев 6 и 8 после Stop строка успешного завершения не обязательна: host отменяет пользовательскую программу.
Если появляется сообщение об ошибке cleanup, звук продолжается или следующий Run недоступен, зафиксируй результат.

## 4. Проверить ошибки размера и HTTP

Выбирай **3, 4, 9** в меню и фиксируй результат каждого:

- **3:** `EXPECTED: InvalidDataException`, звука нет, новых temp-файлов после завершения нет.
- **4:** тот же результат для chunked body; лимит 8192 байта проверяется по реально прочитанным данным.
- **9:** `EXPECTED: HttpRequestException` для HTTP 404, звука нет, временный файл очищен.

После каждого такого сценария выбери 1: это проверяет продолжение работы Music в той же сессии.
Затем введи 0 и отдельно проверь доступность нового Run. Для проверки нового Run после каждого отказа
используй последовательность: Run → 3 (или 4/9) → 1 → 0 → новый Run.
Дополнительная интеграционная проверка 12.10.2026 подтвердила: после пойманных ошибок лимита и HTTP
текущий host возвращается в `Idle`, временный файл очищается, а следующий Run выполняется.
Прежнее предположение о блокировке Run в этом пути оказалось неверным.

**Результат прогона 12.10.2026:** пользователь выполнил все 12 пунктов, приложил консольный лог и три
скриншота, затем подтвердил слышимость звука и ожидаемое поведение. После Stop в 6/8 выполнены новые
запуски; выход через 0 завершился штатным сообщением. Предположение о заблокированном следующем Run
в этом прогоне не воспроизведено и затем опровергнуто интеграционной проверкой текущего host.
Подробности — в [итогах модернизации](../audits/PRODUCTION_READINESS_AUDIT_2026-08-05.md#modernization-results),
источники и границы доказательности — в разделе [аудио smoke](../audits/PRODUCTION_READINESS_AUDIT_2026-08-05.md#modernization-evidence) production-readiness аудита.

## 5. Завершить и сообщить результат

Останови сервер через Ctrl+C. Если остались новые `kid-audio-*.tmp`, запиши имена и размеры;
не удаляй их до фиксации результата. Изменения session/settings для восстановления этим сценарием не требуются.

Удобный формат результата:

```text
1 без лимита: OK / описание проблемы
2 ровно лимит: OK / описание проблемы
7 SoundLoad: OK / описание проблемы
10 chunked/null: OK / описание проблемы
5 SoundStop + повтор + новый звук: OK / описание проблемы
11 Enter при загрузке + возврат в меню: OK / описание проблемы
12 Enter при playback + возврат в меню: OK / описание проблемы
6 UI Stop при загрузке + следующий Run: OK / описание проблемы
8 UI Stop при playback + следующий Run: OK / описание проблемы
3 лимит по заголовку: ошибка ожидаемая? temp очищен? следующий Run доступен?
4 лимит chunked: ошибка ожидаемая? temp очищен? следующий Run доступен?
9 HTTP 404: ошибка ожидаемая? temp очищен? следующий Run доступен?
Оставшиеся новые temp-файлы: нет / имена и размеры
```

Сервер [Serve-MusicDownloadFixture.cs](../../../scripts/manual-checks/Serve-MusicDownloadFixture.cs)
поддерживает `--self-check`: он проверяет WAV/Content-Length/chunked/slow/404
и завершает работу; KID и аудиоустройство не запускает.
