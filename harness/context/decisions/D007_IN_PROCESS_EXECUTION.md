# 🧵 D007. Выполнение пользовательской программы в процессе IDE

## 🔌 Уточнение общего lifecycle D005 (2026-11-03)

Базовое выполнение остаётся in-process через Task.Run и общий KID.Library.
RuntimeSessionOwner библиотеки владеет подключением, token/ID и очисткой;
IDE-контексты передают контролы и делегируют cleanup. CodeExecutionService
ожидает compiler/user code, библиотечный CleanupAsync, Dispose running instance

Резервирование удерживается до этой границы; ошибка блокирует Run и внешний

свои поля, но не добавляет новый режим App-Window из IDE.
[Контракт самостоятельного хоста](../api/Runtime-API.md).

## 🎯 Контекст и задача

В базовом сценарии .KID ученик пишет линейную программу, которая выводит текст, читает ввод и рисует в консоли и графическом поле IDE. Согласно D001, подготовку окружения берёт на себя среда: ученику не требуется создавать собственное окно, настраивать компоненты или организовывать событийное взаимодействие.

При этом учебный API находится в самостоятельной библиотеке `KID.Library`, независимой от проекта IDE, — D005. IDE предоставляет библиотеке средства ввода и вывода, с которыми работают команды пользовательской программы.

Необходимо обеспечить такое взаимодействие, сохранив возможность интерфейса обрабатывать события во время вычислений и ожидания ввода.

## ✅ Решение и причины выбора

**В базовом сценарии пользовательская программа выполняется внутри процесса IDE, вне UI-потока, через `Task.Run` с использованием пула потоков .NET.**

Такая организация сохраняет линейную форму пользовательской программы: вычисления и синхронное ожидание консольного ввода происходят в рабочем потоке, пока UI-поток обрабатывает ввод, обновление интерфейса и команды управления запуском.

Общий процесс позволяет IDE и пользовательской программе использовать один экземпляр загруженной `KID.Library` и предоставленные ей элементы вывода. Библиотека работает с консолью и холстом IDE через обычные внутрипроцессные вызовы и ссылки на объекты.

Это связывает требования D001 и D005: ученик использует простые команды самостоятельной библиотеки, а IDE подготавливает окружение и предоставляет свои элементы интерфейса. Для такого взаимодействия не требуется межпроцессный протокол передачи графических команд и результатов.

Операции с WPF-элементами библиотека направляет в UI-поток через Dispatcher. Пользователю не требуется самостоятельно организовывать эту передачу для обычных команд учебного API.

## 🔭 Сценарий App-Window

Для запуска пользовательской программы в собственном окне **App-Window предусмотрен отдельный процесс**.

Это другой сценарий использования самостоятельной библиотеки: программа работает с элементами собственного приложения. Он является будущим развитием и не заменяет базовый запуск с выводом внутри IDE.

## 📌 Последствия и границы

- IDE и пользовательская программа разделяют процесс и часть состояния среды выполнения. Отдельный рабочий поток не обеспечивает процессную изоляцию.
- Работа библиотеки с WPF-элементами требует передачи операций в принадлежащий им UI-поток.
- Общие ресурсы, включая перенаправление `System.Console`, требуют подготовки перед запуском и восстановления после завершения.
- Остановка программы кооперативна: отдельный поток сам по себе не гарантирует принудительного завершения произвольного пользовательского кода.
- Отдельный проект библиотеки позволяет использовать её в разных приложениях; он не означает автоматического выполнения библиотеки в отдельном процессе.
