# 🧩 D009. Статический фасад для Graphics, Music, Mouse и Keyboard

## 🔌 Уточнение host API D005 (2026-11-03)

Статические учебные фасады сохраняются. KIDRuntimeSession — объект владельца
для внешнего хоста, а не замена Graphics/Music/Mouse/Keyboard в учебном коде.
IDE-контексты передают ресурсы тому же RuntimeSessionOwner. Graphics.SetCanvas
выбирает поле активной сессии; принятые операции сохраняют назначение и scope,
общий стиль не сбрасывается, MouseCanvas/KeyboardWindow остаются фиксированными.
Пары «выбор → рисование» из разных Task сериализует хост.
[Контракт и пример](../api/Runtime-API.md).

## 🎯 Контекст и задача

Согласно D001, ученик должен иметь возможность начинать с простой процедурной программы и сразу работать с графикой, звуком, мышью и клавиатурой.

Для этого учебный API должен требовать как можно меньше предварительных знаний и дополнительных сущностей. Создание объектов и настройка компонентов не должны быть обязательными действиями перед первыми командами.

## ✅ Решение и причины выбора

Предоставить `Graphics`, `Music`, `Mouse` и `Keyboard` в виде **статических фасадов**: тематических точек доступа к соответствующим возможностям `KID.Library`.

Ученик обращается к методам и свойствам непосредственно через имя класса, например:

```csharp
Graphics.Circle(150, 150, 50);
Music.Sound(440, 500);
```

Основная причина выбора — **радикальное снижение количества сущностей на старте обучения**. Такой API воспринимается как простой вызов функций из тематического модуля: ученику не требуется предварительно создавать объекты, разбираться в их связях и организовывать окружение.

По оценке автора проекта, альтернативные формы API значительно менее понятны начинающему ученику. Конкретные рассмотренные варианты не зафиксированы.

Решение развивает образовательный принцип D001: подготовку окружения берёт на себя среда, а ученик начинает с последовательности понятных команд.

## 📌 Последствия и границы

- Для начального использования этих API ученику не требуется создавать экземпляры `Graphics`, `Music`, `Mouse` или `Keyboard`.
- Статический фасад упрощает обращение к возможностям библиотеки, но подготовка ресурсов и управление их временем жизни остаются обязанностью среды выполнения.
- Статическая форма публичного доступа не требует исключительно статической внутренней реализации: фасады могут использовать объекты и компоненты, скрытые от начальной учебной программы.

В текущей реализации за статическими фасадами стоят ресурсы и состояние конкретного запуска: подключённый холст, обработчики ввода и средства воспроизведения звука. IDE подготавливает их перед выполнением программы, а при завершении снимает подписки, освобождает принадлежащие запуску ресурсы и сбрасывает привязки фасадов. Таким образом, простой статический API скрывает от ученика управление жизненным циклом этих компонентов.
