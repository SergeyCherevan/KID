# 🖥️ D010. Статический API консоли с ресурсами конкретного запуска

## 🖥️ Уточнение необязательной консоли D005 (2026-11-03)

ConsoleTextBox в KIDRuntimeOptions явно подключает TextBoxConsole, отдельный
RedirectSystemConsole включает process-wide In/Out/Error. Без них графика,
ввод и музыка доступны независимо. В IDE TextBoxConsoleContext теперь передаёт
контрол и настройку общему RuntimeSessionOwner; сохранение и восстановление
каждого потока, включая partial Init и shutdown failure, выполняет владелец
библиотеки. Хост ожидает свои задачи, затем DisposeAsync до shutdown Dispatcher.

Roslyn rewrite Console.Clear остаётся в IDE. Внешний хост вызывает
TextBoxConsole.Clear явно; самостоятельное подключение не запускает compiler.
Graphics.SetCanvas не переподключает консоль и не меняет streams.
[Публичная сессия](../api/Runtime-API.md) и
[пример с необязательной консолью](../../checks/probes/KID.Library.StandaloneDemo/README.md).

## 🎯 Контекст и задача

В прежней реализации консольный мост требовал ссылки скомпилированной пользовательской программы на `KID.WPF.IDE`. Требовалось убрать эту зависимость, чтобы уменьшить вероятность нарушения работы IDE вызовами из пользовательского кода.

Кроме того, необходимо было установить архитектурное единообразие консольного API с `Graphics`, `Music`, `Mouse` и `Keyboard`: предоставить статическую точку доступа, сохранив управление ресурсами в рамках конкретного запуска.

## ✅ Решение и причины выбора

Разместить консольный API в `KID.Library` в виде **публичного статического класса `TextBoxConsole`**, а время жизни используемых им ресурсов связать с конкретным запуском пользовательской программы.

IDE подключает консоль к своему `TextBox` и перенаправляет `System.Console.In`, `Out` и `Error` через адаптеры библиотеки. Ученик продолжает использовать стандартные вызовы, например `Console.WriteLine(...)` и `Console.ReadLine()`.

Причины выбора:

- **Устранение зависимости пользовательской программы от IDE.** Консольные операции должны обращаться к `KID.Library`, без необходимости ссылки на `KID.WPF.IDE`. Авторская цель — уменьшить вероятность того, что пользователь своими вызовами нарушит работу IDE.
- **Архитектурное единообразие.** `TextBoxConsole` организуется по общему принципу с `Graphics`, `Music`, `Mouse` и `Keyboard`: статический API предоставляет доступ к возможностям библиотеки, а среда подготавливает и освобождает ресурсы запуска.

Статическая форма API не означает бессрочного существования его ресурсов. При запуске создаются привязанные к нему адаптеры и средства обработки ввода и событий; при завершении среда выполняет очистку и восстанавливает исходные потоки `System.Console`.

### 🧹 Поддержка `Console.Clear()`

Для очистки консоли предусмотрено отдельное преобразование пользовательского кода: перед компиляцией вызов стандартного `System.Console.Clear()` заменяется на `KID.TextBoxConsole.Clear()`, очищающий подключённый `TextBox`.

Преобразование проверяет символ метода через Roslyn, поэтому одноимённые пользовательские методы остаются без изменений.

Ранее целевой метод находился в сборке IDE. Перенос в `KID.Library` устраняет необходимость ссылки на `KID.WPF.IDE` и для этой операции.

## 📌 Последствия и границы

- Консольный мост пользовательской программы находится в самостоятельной библиотеке, что развивает архитектурную границу D005.
- В процессе допускается одна активная консольная сессия. Перенаправление `System.Console` затрагивает весь процесс и требует восстановления после завершения запуска.
- Сохранённые адаптеры ввода и вывода привязаны к своему запуску и не переключаются на ресурсы следующего.
- Устранение ссылки на IDE уменьшает прямую связанность с её API. Оно не обеспечивает защитную изоляцию пользовательского кода, который согласно D007 выполняется внутри процесса IDE.
